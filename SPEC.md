# SPEC: novel companion desktop app

Version 0.2, amended in Phase 0 on 2026-10-10 after the source material in `source-material/` was read (see `docs/SOURCE-MANIFEST.md` and `docs/PHASE0-FINDINGS.md`). Amendments are numbered A1 to A39 in the log at the end of section 10 and marked inline as `[A#]`. After I approve it, this file is the single authority: every piece of work is checked against the numbered criteria here.

Each criterion has an ID (for example `FT-4`). A criterion passes only when there is a named automated test or a recorded manual check for it in `PROGRESS.md`.

## 1. Purpose and scope

A single-user desktop app that holds the story bible for a novel and produces a focused brief before each writing session. The app is general `[A16]`: it holds any number of bibles (one per novel, all inside the single database `novel_companion`, switched in settings), and nothing about a particular book is written into code. The first bible, and the example used throughout this spec and the tests' spirit, is East Winds (2025 to 2100, the Sullivan and Li families, San Francisco and Jinan in Shandong `[A1]`).

**In scope:** storing and editing all story knowledge, a visual family tree, timeline and age calculations, session briefs, continuity checks, Claude running inside the app, import from Excel and Word, Google Drive import and backup.

**Out of scope:** replacing my writing editor, multi-user collaboration, mobile, two-way Drive sync, publishing or formatting the manuscript.

## 2. Definitions

- **Entry**: any record in the story bible (a character, event, place, plot beat, and so on).
- **Status**: every entry is `canon` (established in a written chapter), `planned`, or `idea`.
- **Provenance**: every entry is `researched` (with a source note) or `invented`, or unset.
- **Story year**: the year in which something happens in the novel. Backstory may fall before 2025, so years outside 2025 to 2100 are valid everywhere.
- **Reading order**: the position of a chapter in the book, which may differ from chronological order.
- **Current position**: the last chapter in reading order marked as written.

## 3. Architecture

Defaults; Phase 0 may amend them with a stated reason.

- **ARCH-1** Electron app in TypeScript. The main process owns the database, the file system, the keychain, and all network calls. The renderer (React) has no direct network or key access and talks to the main process through a typed interface.
- **ARCH-2** `[A2]` MongoDB (the Atlas deployment I provide) holds the bible, with versioned migrations recorded in a schema-version document. Full-text search is an in-process index built from the database in the main process and updated on every write, tokenizing Chinese by character bigrams and English by words, so it behaves identically against Atlas and against the local MongoDB the tests use. The main process also keeps an in-memory read model of the bible, refreshed on every write, and every deterministic query in this spec (ages, timeline, tree, brief selection, continuity) runs against it rather than round-tripping to the database.
- **ARCH-3** `[A2]` The MongoDB database is the source of truth. Drive is an import source and a backup target. Local snapshots (`BK-1`) are the rollback mechanism.
- **ARCH-4** `[A3]` `[A23]` Claude runs through the Claude Agent SDK from the main process, authenticated with an Anthropic API key held in the macOS keychain (service `novel-companion-anthropic`), set and replaced from the settings screen and never shown in full. Anthropic's SDK terms do not allow subscription login for SDK-built products, so that route is not used. The SDK bundles its own Claude Code binary; the installed CLI is not required. If the key is missing or rejected, the app says so and links to the settings screen. SDK usage and model names are checked against current Anthropic documentation at M6; the settings model lists come from the live models endpoint. The model is a setting per feature (`DB-4`).
- **ARCH-5** `[A2]` The MongoDB connection string, Drive tokens, and any API key are stored in the macOS keychain, never in the database, logs, exports, or the repository.
- **ARCH-6** `[A2]` The app needs a connection to the MongoDB deployment. When it cannot connect, it says so in plain language, offers to open the most recent local snapshot read-only, and never pretends a write succeeded. Claude and Drive are the only features that need any other network access.
- **ARCH-7** No telemetry or analytics of any kind.
- **ARCH-8** `[A16]` `[A22]` Multiple bibles. The app uses exactly one database, `novel_companion`, and never reads or writes any other database on the cluster. Inside it, a `bibles` collection registers each bible, and each bible's data lives in its own collections named `<bibleId>.<collection>` (for example `eastwinds.characters`), so bibles share nothing. The app lists bibles, creates a new empty one, and switches between them. Every list in section 4 that has defaults (families, communities, union types, categories, eras, romanization systems) is seeded per bible on creation and editable per `ED-8`; the East Winds values arrive through import, not from code.

## 4. Data model

All entries share: ID, title, body (rich text, stored as one Markdown string `[A44]`), status, provenance and source note, tags, created and modified times, links to other entries, and revision history.

| Entity | Additional fields |
|---|---|
| Family | name, notes, display color |
| Character | a line on what they are to the story `[A38]`, names (see `CH-2`), birth date, death date, birthplace, family memberships, backstory, voice notes as a list of (story year or age, text) `[A9]`, places lived with year ranges |
| Union | two characters, type (married, partnered, other), start year, end year, end reason |
| Parent link | parent, child, type (biological, adoptive, step, guardian), start year |
| Relationship | two characters, free-text type (friend, rival, employer), year range |
| Book / Part | `[A5]` books contain parts, parts contain chapters; each has a number, title, and summary |
| Arc | name, scope (whole book, Sullivan, Li, a character, or custom), owner character (optional), story year range, summary `[A6]` |
| Chapter | part, reading-order number, title, one or more strands `[A5]` (each: label such as "present" or "backstory", story year or year range, point-of-view character, characters present, places; exactly one strand is primary and supplies the chapter's story year wherever this spec says "story year"), arcs, themes, facts in play (see `KN-3`), written flag, manuscript text, summary, source file |
| Plot beat | arcs (zero or more), chapter (optional), story year, point-of-view character, description, world context note, experience note (how the point-of-view character experiences it), order within arc `[A7]` |
| World event | date or year range, real or invented, category (a user-editable hierarchy, for example Technology > Robotics), regions, places, characters affected, formative flag `[A8]` |
| Era state (was "decade state") | name, year range, technology, climate, economy, politics, daily life `[A8]` |
| Cultural entry | community (San Francisco, Jinan / Shandong, Chinese diaspora in California, evangelical church, or custom) `[A1]`, year range it applies to, age group it is about (everyone, 0 to 18, 18 to 30, 30 to 50, 50 to 70, 70 and over) `[A41]`, generation notes |
| Place | parent place, descriptions by year range |
| Glossary term | term in characters, romanization, language, meaning, usage note |
| Fact | a secret or piece of family history |
| Knowledge record | fact, character, year learned, chapter learned (optional), how |
| Theme / motif | description, appearances (chapters) |
| Open question | question, linked entries, state (open, decided), decision |
| Session log | date, chapter worked on, where I stopped, notes |
| Custom section | see section 5.14 |

Dates may be a full date, a year, or unknown. Lists of types (union types, parent-link types, communities, tags) are user-editable, not fixed in code.

## 5. Features and acceptance criteria

### 5.1 Editing (applies to everything)

- **ED-1** Every field of every entity in section 4 can be created, changed, and deleted through the interface. There is no data that can only be changed by re-importing or by editing the database. `[A43]` Outside the family tree there is no inspector column: an entry is edited on its page, which takes the whole width beside its section list, or in place under its row on the screen that lists it; one row is open at a time and Close puts it away.
- **ED-2** Changes save automatically within one second, with no save button. `[A44]` Every long text field (every `longText` field of the schema, era and community descriptions, line and moment notes, the scene note, the summary to approve, the stop prompt, the capture box and the Claude question) is a rich text box that stores Markdown and shows it formatted, never as marks or tags. Full boxes (prose) take `##` and `###` headings (the entry title is the level above), bold, italic, strikethrough, bullet and numbered lists, quotes and `---` scene breaks; inline boxes (line notes, moment notes, the capture box, the Claude question) take bold, italic and strikethrough. Typing `## `, `### `, `**x**`, `*x*`, `- `, `1. `, `> ` or `---` formats as you go; Cmd+B, Cmd+I, Cmd+Alt+2 and 3 (headings) and Cmd+Alt+0 (body text) do the same; selecting text shows a small toolbar (Bold, Italic, Heading, List, Quote, Strike). There is no underline, font or colour. Pasting from Word or Google Docs keeps bold, italic, headings and lists and drops the rest; pasting Markdown text formats it; Shift+Cmd+V pastes the characters as they are. A box grows with its text to about 70% of the window height, then scrolls; it starts at about six lines for prose, three for notes and two for quick inputs, with a reading measure of about 75 characters. Names, titles and years stay one-line fields. The scene outline (`PL-5`) stays plain text, since its gutter and chapter bars follow its lines. Every read-only view of a long text (Relevant to Session tiles and moments, the Story time era, the glossary table, the import preview, the Chinese preview of `GL-3`) draws it with the same formatting.
- **ED-3** Undo and redo work for at least the last 50 changes in a session, including deletions and tree edits. `[A40]` Every write a screen makes is one step: tree moves and tidies, list items added or removed, the bible's settings (romanization, brief window and budget, community descriptions), the strand year written from Story time, and a restored outline version. Writes that replace the whole bible (a snapshot restore, a backup or file import) and proposal decisions are not steps; their own screens take them back. `[A43]` Undo and Redo sit in the top bar on every screen, with Changes, a popover listing this session's steps newest first (undone steps on top, marked Undone, until they are redone or dropped by a new change); what the last undo or redo did, or why it could not, shows in the status bar. `[A44]` In a rich text box Cmd+Z and Shift+Cmd+Z step the box's own typing history while it holds typing not yet saved, as in a native text field, then the app's history.
- **ED-4** Every entry keeps a revision history. I can view any earlier revision, compare it with the current one, and restore it.
- **ED-5** Deleting moves an entry to a trash from which it can be restored with its links intact. Before deleting, the app lists the entries that link to it.
- **ED-6** Generated content (chapter summaries, briefs, continuity findings) and imported content are editable like anything else.
- **ED-7** Re-import, Claude, and bulk actions never overwrite my edits without showing me the change and getting my approval.
- **ED-8** Type lists, family names, tags, section names, and decade ranges are editable. Renaming one updates every entry that uses it.
- **ED-9** Any entry can be linked to any other by typing `@` and searching. Each entry shows what links to it. `[A44]` In a rich text box the pick is stored as the text `@Title` and adds the link; where the text names a linked entry it shows as a chip.
- **ED-10** Invalid input (for example a death date before a birth date) is flagged at the field with a plain explanation. Warnings never block saving; this is fiction and I may mean it.

### 5.2 Characters

- **CH-1** Create, edit, and delete characters with all fields in section 4. A character can belong to zero, one, or several families.
- **CH-2** Names support: full name, name in Chinese characters, romanization, name order (family name first or last), birth name, married name, nicknames, and what each other character calls them.
- **CH-3** The character page shows current-position age, a personal timeline (own events, world events in their lifetime, chapters they appear in), relatives, and what they know. The page opens on the line about their place in the story and their status, then Description, Family and Life; Names, What they know, the Personal timeline, Backstory, Voice notes and Source sit lower, each behind a caret that remembers whether it is open on this computer, with a one-line hint beside the title (the word count, the families and relatives, the years and birthplace) `[A38]`. The list of facts they do not know is gone `[A38]`.
- **CH-4** A character with an unknown birth year is allowed and is reported as "age unknown" everywhere, never estimated.

### 5.3 Family tree

- **FT-1** One overall tree shows every family together, including the links between the Sullivans and the Lis. It always shows everyone; the family and lineage filters are gone, and collapsing a branch (`FT-8`) is the way to hide part of it `[A45]`.
- **FT-2** The tree is fully editable in place: add a person (from the toolbar or the inspector); add a parent, child, sibling, or partner from any node; change or remove any link; change link and union types; delete a person with Remove on the inspector (following `ED-5`) `[A38]`. Two people already in the tree are linked by dropping one on the other (`FT-11`); the Link someone form is gone `[A38]`. The inspector lists the person's family at its foot from the top down: Parents, then Partners and Siblings, then Children; each union and parent link keeps its type, an editor for its years, and Remove, siblings follow from shared parents, and each group has its own Add button whose form opens under it `[A45]`.
- **FT-3** Edits in the tree and edits on character pages are the same data. A change in one appears in the other immediately.
- **FT-4** The tree supports multiple unions per person, ended unions, half-siblings, adoptive, step, and guardian links (drawn distinctly from biological ones), people with one or no known parents, and people in no family.
- **FT-5** The tree follows the story year and redraws for any year: who is unborn, alive (with age), or dead, and which unions are active. The tree has no year control of its own; the story year is set from the status bar's Story time button or Cmd+T (`TM-1`) `[A45]`.
- **FT-6** The app prevents a person from being their own ancestor. It warns, without blocking, on: a parent under 12 or over 60 at a child's birth, a child born more than a year after a parent's death, overlapping unions, and a child born before a union started.
- **FT-7** Each node shows name, years, and status. Selecting a node opens the character for editing without leaving the tree. The tree inspector edits Name, Name in Chinese characters, In the story, Description, Birth, Death and Families; Backstory is a link that opens the Backstory screen on the person; status, provenance, source note, source location, tags and links are not shown there and stay stored `[A45]`.
- **FT-8** The tree stays readable and responsive with 200 people across six generations: pan, zoom, collapse and expand branches, and fit to window. The screen is one toolbar row (Add person, Fit to window, Tidy layout, Export, Full screen, and the warning count) above the tree, which fills the rest of the middle column down to the status bar with no page scroll; the inspector keeps the right column and is the only inspector on this screen. The legend is a small overlay in the tree's bottom left corner that opens and closes, and the `FT-6` warnings show in the inspector while nobody is selected; the warning count clears the selection to show them `[A45]`. A Full screen control shows the tree and its inspector on the whole screen; Escape or the control leaves it `[A26]`.
- **FT-9** One Export control saves the tree as a PNG image, always in the light theme, through a save dialog. There is no PDF export of the tree `[A45]`.
- **FT-10** Layout is stable: adding one person does not rearrange unrelated branches.
- **FT-11** `[A38]` People are dragged: a person dropped in empty space stays there (the row snaps to the generation grid, the place is stored with the layout, nobody else moves), and Alt with an arrow moves the focused person one slot. A person dropped on another opens a menu under the pointer: make them that person's parent, child or partner (the first link or union type, changeable in the Links list; self-ancestry is refused in plain words and nothing is written), just move them there, or cancel. Nothing is dragged while read-only (`ARCH-6`).

### 5.4 Timeline and ages

- **TL-1** All age and alive-or-dead results are computed in code, never by a model.
- **TL-2** For any year, the app lists every character as alive (with age), dead (with year of death), not yet born, or unknown.
- **TL-3** With year-only birth data, age in year Y is Y minus birth year. With full dates, age is exact for a given date.
- **TL-4** In the year of death a character is listed as alive and flagged as dying that year.
- **TL-5** For any character and year, the app lists the world events they have lived through and their age at each.
- **TL-6** A timeline view shows world events, decade states, chapters, and character lifespans on one axis, filterable by family, place, and status. Items can be edited from the timeline. World events also have a strip of year columns, titles only, each opening its event: the whole span on the World events section, and the SB-2 window in every "Relevant to Session" strand `[A33]`.
- **TL-7** Two characters can be compared: ages side by side across a year range.

### 5.5 Plot

- **PL-1** Arcs exist for the whole book, the Sullivan family, the Li family, and any I add. A beat or chapter can belong to several arcs.
- **PL-2** `[A6]` An outline view is a grid: one row per chapter in reading order (grouped by book and part), one column per story year, with each chapter's strands and each arc drawn as spans across the years they cover. It can be flipped to story-year order. This reproduces the "High Level" sheet of my workbook.
- **PL-3** Beats and chapters can be reordered by dragging. Reading order and chronological order are tracked separately.
- **PL-4** Each chapter shows its beats, characters present with ages in that story year, places, themes, and facts in play.
- **PL-5** `[A36]` The Outline screen opens on a scene outline: one long bulleted text per bible, written in page order and independent of the chapter titles. A scene is a top-level bullet with text, numbered in order; an indented bullet belongs to the scene above it; a line without a bullet is a heading. Enter continues a bullet, Cmd+] and Cmd+[ indent and outdent (Tab leaves the field, `NF-2`), an empty bullet ends the list. It autosaves like an entry (`ED-2`) but lives in `meta`, not in an entry. Every change is kept as a version in `sceneOutlineVersions`: saves within ten minutes share one version, a restore is a new version of its own, and an outline written before versioning gets its old state as its first version. Beside the text the chapters are listed in reading order, each with its title and its story year (the primary strand's year, so the `PL-2` grid follows it) editable in place. A chapter is placed on the scenes by dragging its row onto a scene (or with Place next); it then appears as a block on a track beside the text, over the lines of its scenes, in its own colour, which also tints those lines in the gutter. Dragging the block moves it, pulling its top or bottom edge changes where it starts or ends, and from the keyboard the arrows move it, Shift and Alt with the arrows move its end and start, and Delete takes it off (Take off on the row does the same). Chapters are reordered by dragging rows among themselves, into another part too, or with Alt+Up and Alt+Down on the title. The scene ranges are kept with the outline and versioned with it; ranges past the last scene or shared by two chapters are named on the chapters and shown side by side on the track. Renames, year changes and moves are ordinary entry writes with undo (`ED-3`) and are disabled while read-only (`ARCH-6`). The year grid of `PL-2` and `KB-3` is one click away, remembered on this computer; it fills the screen (year columns stretch to the width; a picked row, arc or beat opens below the grid, the whole width of the screen `[A43]`).
- **PL-6** `[A37]` The scene outline and the chapters are one flow that scrolls as one: each chapter is a heading in the text, in reading order under its book and part, with its title and story year editable in place, its scene count, and its own scenes below it; the scene numbers run on across the chapters. A chapter's section starts at a line of the text (`breaks`, kept and versioned with the outline; the scene ranges are derived from them, and an outline saved with ranges only starts each chapter at the first scene of its range). Moving a chapter, by dragging its grip onto another chapter or a part or with Alt+Up and Alt+Down on its title, moves its scenes with it, and undo moves them back. ↑ Scene and ↓ Scene on a heading start the chapter one scene earlier or later (a scene carries its indented lines). Cmd+Enter in the text makes a new chapter right after the one the caret is in, in its part and story year, holding the lines from the caret on, as one undo step; undoing it gives the lines back. Up on a section's first line and Down on its last carry on into the next section; Enter on a title goes down into its scenes. A chapter that goes to the trash hands its lines to the section above it, so no line is lost. Each heading shows the era of its year and the world events going on in it (those that begin that year first), each opening its entry; between two chapters a line says the time that passes ("8 years later, 2040", "Back 30 years, to 2045") and lists the world events that begin in between. The year grid draws a world band under the year header (eras named across their years, events as dots and bars stacked so none hides another), lines every ten years, and the story year of each row beside its title; every year in the header is a button (arrow keys walk the years), and a picked year is banded across the grid and opens a panel with its era, its world events, the chapters set in it (main strand or backstory, each opening the chapter), and Make it the story time.

### 5.6 World events and decade states

- **WE-1** Events can be a single date, a year, or a range; real or invented; linked to places and characters; filed under a category and regions `[A8]`. The category list is editable per `ED-8` and the timeline (`TL-6`) can be filtered by it.
- **WE-2** Era states cover 2025 to 2100 with no gaps by default; the default eras are the sections of my World Development document, not fixed ten-year blocks `[A8]`. Ranges are editable, and overlaps or gaps are flagged.
- **WE-3** For any year, the app returns the era state that applies and the events up to that year.

### 5.7 Culture, places, glossary

- **CU-1** Cultural entries are organized by community and by the years they apply to, so the same tradition can be described differently in 2030 and 2080.
- **CU-2** For a given community and year, the app returns the entries that apply.
- **CU-3** `[A41]` `[A42]` The Cultural data screen is one community at a time: a description of the community overall, then its cultural lines for the story year's decade (the year control at the top moves it) grouped by age group (everyone, 0 to 18, 18 to 30, 30 to 50, 50 to 70, 70 and over). A line is added under its age group by typing it and pressing Enter (it covers that decade); its text and its note edit directly and save when the field is left (the community description is a full rich text box and the note an inline one, `ED-2` `[A44]`); its age group and its decade are selects on the row; Remove moves it to the trash. A community is added, renamed and removed (with its lines, as one undo step, after one confirmation) on the screen. Everything is edited where it sits, with no side panel `[A43]`; each change is one undo step.
- **WT-1** `[A41]` `[A42]` Writing tools, a screen of its own in the rail: synonyms, antonyms, words that mean the same, rhymes and near rhymes, words that sound or are spelled alike, related words, adjectives for a noun, nouns an adjective describes, homophones, and a definition, from Datamuse (free, no key) through the main process. A result word runs the same lookup again. Without a connection the screen says so in plain words.
- **PC-1** Places nest (city, district, building) and hold descriptions by year range. `[A43]` On the Place tree a picked place opens its editor in place, under its row.
- **GL-1** Glossary terms store characters, romanization, language, and meaning. One romanization system per language is set in settings, and terms that do not follow it are flagged. `[A43]` A flagged term on the Romanization screen opens its editor under its line; Edit on a row of the Glossary table opens the term's editor in a row right under it.
- **GL-2** Searching finds a term by its characters, its romanization (with or without tone marks), or its meaning.
- **GL-3** `[A10]` Chinese characters are shown as characters everywhere (names, glossary, body text, labels, tree nodes). Hovering over them, or focusing them with the keyboard, shows the romanization and meaning from the matching glossary term; character names link to their glossary term automatically, and a run of characters with no glossary term shows a one-click "add to glossary" action.

### 5.8 Knowledge states

- **KN-1** For any fact, the app shows who knows it and from when. For any character and year, it shows what they know and do not know.
- **KN-2** A character cannot be recorded as learning a fact before they are born; this is a warning per `ED-10`.
- **KN-3** A chapter can list facts in play: which characters act on which facts. This is what the continuity check uses in `CC-2`.

### 5.9 Themes, open questions, session log

- **TH-1** Themes and motifs list every chapter they appear in, with a note for each appearance.
- **OQ-1** Open questions can be linked to any entry, marked decided with the decision recorded, and filtered by state. `[A43]` On Sessions a picked question opens its editor in place, under its row; New question opens its form at the top of the questions, and the new question then opens under its row.
- **SL-1** Ending a session prompts for where I stopped. The next launch shows that note first. `[A43]` On Sessions a picked session log opens its editor in place, under its row, one log or question at a time.

### 5.10 Manuscript

- **MS-1** Chapters can be imported from Word files or Google Docs and linked to their source file. Text formatting that carries meaning (italics, scene breaks) is kept.
- **MS-2** Marking a chapter as written offers a generated summary. Nothing is saved until I approve or edit it.
- **MS-3** Marking a chapter as written offers to promote the planned entries it establishes to `canon`, as a list I approve item by item.
- **MS-4** Re-importing a changed chapter shows a text diff and marks its summary as possibly out of date.
- **MS-5** `[A4]` The app never edits the manuscript. There is no code path that writes to a manuscript file or Google Doc; the manuscript text held in the bible is a read-only import.

### 5.11 Session brief

- **SB-1** Inputs: a chapter, or a story year plus point-of-view character, with optional place and other characters present.
- **SB-2** Entries are selected by deterministic queries, defined here. If the chapter has more than one strand, steps 1 to 6 run once per strand and the brief has one section per strand, the primary strand first `[A5]`:
  1. Characters present, with ages. If none are listed, the point-of-view character and their living parents, partners, children, and siblings.
  2. The era state covering the story year.
  3. World events in a five year window around the story year: the three years before it (the window is a setting) through the year after it `[A33]`, plus any event marked formative within the lifetime of a character present, plus events linked to the chapter's places. Events after the story year stay under "Planned ahead" (SB-5).
  4. Cultural entries matching the setting's communities and the story year. The setting is the strand's places; with none, the place the point-of-view character (else the first character present) lived in that year. Its communities are every community from the place out to the outermost place, nearest first, then each one's parent in the communities list `[A35]`.
  5. Place descriptions for the story year.
  6. What each character present knows, and facts others present know that the point-of-view character does not.
  7. Summaries of the three previous chapters in reading order, the previous chapter in each of this chapter's arcs, and the previous chapter with the same point-of-view character.
  8. Beats planned for this chapter, and unresolved beats from earlier chapters in its arcs. An unresolved beat is one in any of this chapter's arcs whose story year is at or before this story year and which is assigned to no chapter or to a chapter not marked written `[A18]`.
  9. Glossary terms, themes, and open questions linked to anything selected above. Linked means: a glossary term linked to a selected entry or whose characters appear in a selected character's names; a theme with an appearance in a selected chapter or this chapter; an open question linked to any selected entry `[A18]`. Decided questions linked the same way are included with their decision, under their own heading ("Decided"), separate from still-open questions `[A24]`.
  10. The last session log note for this chapter.
- **SB-3** The selection is saved as a manifest of entry IDs. For the same inputs and data, the manifest is identical every time.
- **SB-4** Claude writes the brief from the manifest's contents only. Every item in the brief cites entry IDs, and code verifies each cited ID is in the manifest; anything that fails is flagged visibly.
- **SB-5** The brief keeps canon and planned material visibly separate, and never includes events after the story year except under a labelled "planned ahead" heading.
- **SB-6** If the selection exceeds the size budget (measured in characters of the selected entries' text, default 40,000, a setting), items are dropped in this fixed priority order, lowest first: open questions, themes, glossary, place descriptions, cultural entries, world events beyond the window, previous-chapter summaries, beats, knowledge, era state, characters present, session-log note `[A18]`. The brief says what was left out. The three DB-2 lead sections are never dropped; if they alone exceed the budget, all are kept and the brief says it is over budget `[A25]`.
- **SB-7** If Claude is unavailable, the app shows the selected entries as a structured brief with no synthesis.
- **SB-8** Briefs are saved, editable, linked to their chapter, and exportable as Markdown and PDF.
- **SB-9** I can add or remove entries from the selection and regenerate.
- **SB-10** `[A28]` A Relevant to Session view, reachable from every screen, shows the `SB-2` selection live for the chapter strand picked in Writing (or a story year plus point-of-view character when none is picked): characters present with ages, world events, cultural expectations, places, knowledge, beats, previous chapters, and linked glossary terms, themes, and questions. Every item opens its entry. It is the same selection the brief uses, with no Claude involved. `[A35]` The chapter heads the view; world events come first, then the backstory of the chapter's backstory years (each character's backstory passages dated from their text, with the passage leading up to them and any pinned passage; a year can be corrected and a passage pinned in place), the characters present by name and age only, and the cultural context of the setting for the story year (with a way to change the strand's places, and a Cmd+K prefill when nothing covers that year). Everything else in the selection folds under "More". With no strand picked, the primary strand is the scene.

### 5.12 Continuity check

- **CC-1** Runs on one chapter or the whole manuscript, on demand.
- **CC-2** Structural checks, in code: a character present in a chapter while dead or unborn in its story year; a character acting on a fact before the year they learn it (withdrawn by `SM-2` `[A39]`, facts no longer exist); an event linked to a chapter as having happened but dated after its story year; tree warnings from `FT-6`; a chapter's story year outside its point-of-view character's lifetime.
- **CC-3** `[A20]` Alignment checks, by Claude: the chapter text is compared with the entries selected for it and with the plot as stored: the chapter's strands and years, its beats, beats in its arcs dated before its story year, chapter order, and the facts in play. Each finding quotes the chapter passage with its line numbers, cites the conflicting entry or beat, and explains the conflict. The check runs on one chapter or the whole manuscript at any time (`CC-1`) and uses the model configured for continuity, default `claude-opus-5-5`.
- **CC-4** `[A20]` Each finding offers three resolutions. **Manuscript wins:** the finding carries a prepared change set to the bible (the entries, beats, or strands that would make the bible match the chapter); the change set is shown as a diff, and one click applies all of it through the normal write path, recorded in revision history and undoable. **Rewrite recommended:** the finding becomes a rewrite task listing the exact manuscript lines (chapter, line numbers, quoted text) and a plain description of what must change to match the bible; it never contains replacement prose (`AI-4`). Open rewrite tasks are listed on the dashboard (`DB-1`) and on the chapter. **Dismiss.** Dismissed findings do not reappear unless the text or the entry changes.
- **CC-5** Structural checks produce no findings on the fixture novel's clean chapters and find every planted structural error (section 7).

### 5.13 Claude panel `[A19]` `[A21]`

- **AI-1** A question panel is available from every screen: I ask questions about the bible and the manuscript, with streaming responses, a stop button, and saved conversation history. Claude also runs inside four features, each started by a named control and fed only by deterministic selection: session briefs (`DB-2`, `SB-4`), alignment checks (`CC-3`), chapter summaries (`MS-2`), and import proposals (`IM-5`). Every run streams, can be stopped, and is saved with the feature that produced it.
- **AI-2** In the panel Claude reads the bible through read-only tools: search entries, get an entry, query the timeline for a year, get a person's relatives, get a chapter. The panel shows which entries were read for each answer; each feature run shows which entries it was given.
- **AI-3** Claude has no tool that writes to the bible. It can only submit proposals (create, change, delete, link), which appear in a review queue showing the exact change. Nothing is saved until I approve, and I can edit a proposal before approving.
- **AI-4** Claude never drafts prose for the novel. No screen, setting, or control asks Claude for prose, the system prompt for the panel and for every feature forbids it, and if I ask for prose in the panel Claude declines in one sentence and offers the bible facts instead. A test asserts that every system prompt contains the prohibition and that a recorded "write the scene" request in the panel yields a refusal with no prose.
- **AI-5** Imported text is treated as material to analyse, never as instructions to Claude.
- **AI-6** On first use, the app states plainly that content used in Claude features is sent to Anthropic, and which features do that.
- **AI-7** Failures (no network, bad key, rate limit) show a clear message and never lose my input or corrupt data.

### 5.24 Everything on screen is a field `[A47]`

Decided 2026-10-22 from the edit audit (`docs/EDIT-AUDIT-2026-10-22.md`: 117 things the screens show, 49 editable in place, 24 edited elsewhere, 25 locked, 11 hidden, 8 derived). The rule: any value you can read, you can click and change, right there, with undo. Editing never leaves the screen the writer is on and never covers what they are reading: a field looks like text until it is picked, opening one does not move the text around it, opens no dialog and scrolls nothing, and the reading layout is the same before and after. The three screens the writer looks at most while writing (Relevant to Session, the Story time dialog, the Continuity checker) come first. Where a criterion below conflicts with an earlier one, this section wins.

- **IP-1** One editing primitive. `Editable` (renderer, `workspace/editable/`) draws a stored value as text and becomes a field on click, Enter or Space: kinds `text`, `year`, `number`, `rich` (the `A44` box), `select` (with "Add new..." that creates the list item without leaving the field), `chips` (a list of references or list items, add from a picker, remove with a button on the chip) and `date` (the one-box birth and death of `SM-1`). Enter or blur saves, Escape reverts, the field takes the text's place and size, a saved tick shows briefly, every save is one undo step through the entry write path or a `run` op, and a value that fails validation shows the `ED-10` explanation at the field and keeps the old value. Keyboard reachable with a visible focus ring, labels in the primary text colour, both themes, read-only with the reason under `ARCH-6`. Every screen that draws a stored value draws it with `Editable`, except where a criterion says the value is derived or locked and why. The `Characters` page proves it: the name is a field, not an Edit name button, and a list row renames in place.
- **IP-2** Relevant to Session is the writing desk. The heading renames the chapter. The story year and the point of view are fields on the writing strand. A character tile edits name, Chinese name, birth, death, In the story and Description in place; its moments edit in the tile, and "Add a moment" creates one for that person at the story year. "In this scene" is a chip row over the strand's characters present, with add (a picker whose "Add new..." creates a character) and remove, written to the strand as one step. The world events strip has "Add an event in <year>", which creates an event at the story year and opens its title as a field. A cultural gap offers "Write it yourself" beside the Claude button: a line is created in that community for the decade and age group and opens as a field. Every entry under More and in the selection preview has Remove and Keep (`SB-9`) before a brief is generated, and no raw ID is printed anywhere. The chapter's manuscript text has "Re-import" (`IP-18`).
- **IP-3** Outline bars carry the strand. A bar shows a strand chip; clicking it (or Enter on it) opens a popover anchored to the bar with the writing strand's label, point of view, characters present and places, and the backstory strand's year, each an `Editable`, without opening the chapter page; Escape closes it and the focus returns to the bar. The first part's title shows as a divider above the first chapter and renames there like every divider. The written flag is a toggle on the bar.
- **IP-4** Grids are drawable. Backstory: a lifespan bar's ends drag to set birth and death (one step each; Shift with the arrows does the same on the focused bar), the character name row opens the person's page, and a moment moves to another person through the Whose moment select in its dialog (`A49`). Backstory markers are 14px dots in 48px rows with a hit area 6px past the dot, so a near miss opens the moment rather than adding one. Both grids: an era band's edges drag to set its start and end, double-click (or Enter) on a gap in the band creates an era over the gap and opens its name as a field, and double-click (or F2) on a marker's label renames it in place; on Backstory a double-click opens the moment's dialog with What happens open instead, and F2 still renames in place (`A49`). The year axis, the world-around window and the picker's reach read the bible's numbers (`IP-11`).
- **IP-5** Story time dialog rows are links and fields. Each person's row shows the name as a link to their page and birth and death as fields; the era panel edits name, start, end and body in place; each chapter strand in the year opens its chapter on the Outline; Lived through and Compare rows link to the person.
- **IP-6** Undo everything. Typing in the scene outline records one step per pause (the `A44` rule); regenerating a brief is one step, and the Regenerate button says "This replaces your edits" when the text was edited; adding a note to a cultural line is a step; every write made under `IP-1` to `IP-18` is a step.
- **IP-7** Continuity cards edit the finding. A finding card edits its text, quote and "what must change" in place, carries a resolution note field, and links to the finding page. On the Manuscript tab the approved summary shows and edits on the chapter row, "Mark as written" gains "Not written after all" once set, and a rewrite task's text edits in place on Sessions.
- **IP-8** Lists reorder and re-parent. Every list item moves with drag, Up and Down, and in a hierarchical list takes a parent in place; the stored order is the order shown everywhere (the World events rows, every select). `regions` is a list seeded from the regions events use; an event stores region item IDs, so renaming a region renames it on every event. ### 5.25 Capture routing `[A48]`

Decided 2026-10-22 from the Capture Router design (`docs/CAPTURE-ROUTER-2026-10-22.md`, design page https://claude.ai/artifact/7s493dgEerJey1gWmiYSAM). The rule: a line typed into Cmd+K finds its section, community and years before Claude is asked anything, so most captures cost nothing and the rest cost a fraction of `KB-6` today (about 2,750 fixed tokens plus four to eight tool turns, each resending everything).

- **CR-1** Routing is local and free. A pure router in `src/shared/domain/captureRouter/` (no Electron, MongoDB or React) takes the capture text, a `RouterIndex` built from the bible's lists and entries, the story year and the writing strand's community, and returns a `CaptureRouting`: the facts, what each resolved, its scores, its section, its drafts and its route. The renderer and main build the same index from the same documents and run the same function, so they agree. Nothing is sent to Claude before the route is known.
- **CR-2** Facts and years. The text splits into sentences; each sentence is a fact routed on its own. "starting around 2065", "from", "after", "in" and a bare year set the start; "by 2070" and "by the 2070s" set the start and leave the end open; "until", "through" and "to" set the end; "the 2060s" is 2060 to 2069; "2063 to 2066" is a span. A fact with no year takes the year of the fact before it in the same capture, else the story year. A cultural line with an open end stores the bible's timeline end.
- **CR-3** Names resolve against the bible. Characters by full name, first name and Chinese name; places by name, carrying the place's community; communities, event categories and age groups by their labels and by the aliases and cue words of a lexicon keyed by list item ID (`lexicon.ts`; an item the lexicon lacks matches by label only); glossary terms by their characters. A name inside a longer match is not the subject ("Sydney's husband" is its own character, "Siyuan's temple" is a place). A capitalised word mid-sentence that matches nothing is an unknown name. A demonym plus a place prefers the place's community, the demonym's community second; a demonym alone maps to its national community; nothing resolved leaves the community to be asked, the writing strand's community first.
- **CR-4** Sections score by weighted cues (the lexicon lists every cue with its weight and a plain label the box shows): a group that starts to say or do something, custom and expectation words, an age group, a demonym, a community named, a place as subject (cultural data); a character named, a life verb (moment); a public event word, a category cue, a year with no character, a government or bloc as subject (world event); place words (place); Chinese characters, a word explained, a quoted word (glossary term); a question mark, hedging words (open question); a person introduced (character). A question mark cuts every other section to a quarter; a group as subject discounts the moment reading; a character as subject discounts the world event reading.
- **CR-5** Three routes. Route A (local) when the top section holds at least 55% of the points, leads by 20, every name resolved, no judgment flag, and the section's required fields are filled or can be asked for with a chip. Route B (fast) when the top section holds at least 40% but a name is unknown, a category must be picked, several entries must be written, or a quoted word may be a glossary term. Route C (full) otherwise, and whenever the writer asks for it. The thresholds are constants in the router now and may become a setting. A wrong route costs nothing to fix: changing the Section chip re-routes.
- **CR-6** Route A files from the box, without Claude. Enter runs the router. For a Route A fact the box shows chips (Section always; Community, Age group and Years for cultural data; Character and Year for a moment; Category and Year for a world event; Community for a place) and the drafts as the `ED-7` diff; a chip is live and a change re-routes; a missing required field is a highlighted chip the writer fills. File it (Cmd+Enter) writes the ticked drafts through the entry and list channels as one undo step (`ED-3`), new list items first (`IP-17`), status idea, source note "From a capture on <date>, filed without Claude." Nothing is written before File it. Ask Claude instead sends the fact on Route C with the chips as hints; Alt+Enter in the box sends every fact on Route C; a card a chip moves to Route B or C waits with a Send to Claude button rather than sending at once. Review later saves the facts the box would have filed as the `KB-7` open question and leaves sent proposals pending. Escape closes the box and writes nothing.
- **CR-7** Route B is a sixth Claude feature, `captureFast`, default model Haiku 5.5, `claude-haiku-5-5` (a setting, `DB-4`; disclosed in `AI-6`; instructions editable, `IP-15`). No tools. The prompt carries the fact as material (`AI-5`), the resolved candidates with their IDs, the section's fields, the existing titles nearby (the community's lines, the character's moments, or the top-level categories) and the router's notes. Claude returns proposals as JSON in the shape of `propose_change`, validated the same way; it may mint a list item and never deletes. The proposals wait in the box for approval as `KB-6`. It may answer "cannot place" with a reason instead, and the box then offers Route C with one click. The system prompt carries the prose prohibition (`AI-4`).
- **CR-8** Route C is `KB-6` with hints. The lists are trimmed to the sections that scored: communities always, event categories only when a world event scored (top level first, plus the subtree of any matched category), languages only for a glossary term. The prompt carries a block of the candidates the router resolved so Claude skips the search turns, and the router's section guess. In a capture run `get_entry` returns a capture view (title, years, links, and the first 600 tokens of body and backstory) instead of the whole document. The system prompt and tools are a stable prefix so the SDK can cache them; what the SDK does is verified and recorded in `ARCHITECTURE.md`.
- **CR-9** Mixed captures. The facts of one capture show as one list of cards in order: Route A cards with their chips, Route B and C cards streaming as today. The hints sent with the text say which facts Claude handles and what the writer changed, and carry IDs and numbers only (`AI-4`); main reruns the router on the text with the hints and gets the same facts. One File it approves everything ticked (Route A written locally, B and C approved as proposals) as one undo step.
- **CR-10** Tests. The twelve lines of the design page are a routing fixture with their expected route, section, community, years and age group, run against an index built from a small East Winds slice. The `AI-4` test covers `captureFast`. A test shows Route A writes nothing before File it and files as one undo step. The free-text channel test (`AI-4 KB-6`) stays as it is: hints carry no text.

**Verification protocol, for every milestone**

1. The builder subagent receives the milestone's criteria and writes code and tests.
2. The architect runs the full suite itself.
3. A reviewer subagent with fresh context receives only this spec and the code. For each criterion it reports pass or fail with evidence: the test name and what the test actually asserts. A test that exists but does not really exercise the criterion is a fail.
4. Failures go back to a builder with the specific evidence. Repeat from step 2.
5. On a full pass, `PROGRESS.md` records each criterion, its status, and its evidence, and the work is committed.
6. Earlier milestones' tests keep passing. A regression blocks the current milestone.

The spec is not changed to make a failing criterion pass. If a criterion turns out to be wrong or impossible, the architect stops and asks me.
