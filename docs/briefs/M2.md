# M2 brief: characters and family tree

Criteria: CH-1 to CH-4, FT-1 to FT-10. Read first: `docs/ARCHITECTURE.md`, `SPEC.md` sections 2, 4 (Character, Union, ParentLink, Relationship rows), 5.2, 5.3, 6 (NF-1 tree redraw under 500 ms with 200 people, NF-2 keyboard), 7 (the fixture people table is the tree you must render), and the mockup `mockups/tree-timeline.html` (read the HTML; the tree section is the reference for layout, link styles, year control, inspector, warnings, and copy). Then the existing code from M0 and M1 under `src/` and `tests/`; build on the generic editor and repository, do not fork them.

Deliverables, keeping `npm test` green:

1. **Pure tree logic** in `src/shared/domain/tree.ts`: build a graph from characters, unions, parent links; generations from parent links; a deterministic layout (couples adjacent, children centred under their union, stable ordering by creation order so adding a person leaves unrelated branches in place, FT-10); ancestors and descendants of a person (FT-1 filter); the FT-6 validations as pure functions returning warnings (parent under 12 or over 60 at a child's birth, child born more than a year after a parent's death, overlapping unions, child born before its union started) and the one hard refusal (a person as their own ancestor). Unit tests against the fixture with hand-written expected layouts for a small subtree and expected warnings; a generated 200-person, six-generation tree must lay out in well under 500 ms (T-6 style test with a timing assertion).

2. **Ages** are already in `src/shared/domain/ages.ts` from M1 or must be added now per TL-3 and TL-4 (year-only: Y minus birth year; full dates exact; year of death counts as alive and flagged dying; unknown birth reports age unknown, never estimated, CH-4). The tree's year control uses the same function.

3. **Character page** (CH-1 to CH-4): all name fields from CH-2 including "what each other character calls them" as a list of (character, name); families (zero, one, or many); current-position age (from the current story time setting, or the last written chapter's year if no story time is set); personal timeline computed from the character's beats, world events in their lifetime with age at each, and chapters they appear in; relatives derived from unions and parent links (parents, children, siblings and half-siblings, partners with union type and years); what they know (knowledge records). Chinese names render as characters with the GL-3 hover and keyboard focus showing romanization and meaning from the glossary (stub the glossary lookup against the glossary collection; GL-3 is verified fully in M4).

4. **Tree view** (FT-1 to FT-10): SVG rendered from the layout; whole tree with both families and their intersection; filters: all, one family, ancestors and descendants of a chosen person; node shows name, years, status chip; union lines married solid, partnered dashed, ended unions marked with the end year; parent links biological solid, adoptive dashed, step dash-dot, guardian dotted; people in no family and people with one or no known parents render correctly; the year control (a range input and a numeric input bound to the story time) redraws every node as unborn, alive with age, dying this year, dead with year, or unknown, and marks unions active or ended (FT-5); selecting a node opens the character in the inspector using the M1 generic editor, and edits there redraw the tree immediately (FT-3, FT-7); in-tree actions: add person, add parent, add child, add sibling, add partner from any node, change or remove any link, change link and union types, delete a person through the ED-5 trash flow (FT-2); warnings list from FT-6 shown and never blocking; the self-ancestor refusal shown as a plain message; pan by drag, zoom buttons and wheel, collapse and expand a branch, fit to window (FT-8); export as PNG and PDF through Electron's `webContents.printToPDF` for PDF and canvas rasterization for PNG, saved with a save dialog (FT-9).

5. **Tests**: unit for every pure function with the fixture's known relationships (for example H5 has parents H3 and Z3, H6's parent link to H4 is adoptive from 2015, X1 has no family, U1 renders with unknown years); integration for the tree queries against the loaded fixture; e2e: build a tree by hand through the interface that matches the fixture people table (the T-4 "building a tree by hand" flow: create every person, every union, every parent link through tree actions, then assert the layout graph equals the fixture's graph), move the year control to 2040, 2041, and 2075 and assert the on-screen states match `fixtures/expected/tl2.json`, edit a birth year in the inspector and see the node change, delete and restore a person; a performance test that generates 200 people across six generations, loads them, and asserts tree redraw under 500 ms in the renderer (measure in e2e with `performance.now()`).

Constraints: no em dashes anywhere; `fixtures/expected/` untouched; pure logic in `src/shared/domain/` with no Electron, MongoDB, or React imports; test names start with the criterion ID. Report at the end: `npm test` tail, criterion to test names table, files changed, and anything not done with the reason.
