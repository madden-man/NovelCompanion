**Corrections (2026-10-11).** The brief's intent stands; match the schema and registry as built.

- Finding states are exactly `open`, `manuscriptWins`, `rewrite`, `dismissed` (the `Finding` schema in `src/shared/schema/story.ts`). There is no `resolved` or `rewriteTasks` collection: Rewrite recommended sets state `rewrite` on the finding, which carries the quote, line numbers, and what must change, with no field for suggested text. - The `alignment` feature is `src/main/claude/features/alignment.ts`, added to `FEATURES` in `features/index.ts` (the AI-4 test walks that list). Its channel and handler follow "Adding a feature" in `docs/ARCHITECTURE.md`.

Deliverables, keeping `npm test` green:

1. **Structural checks** `src/shared/domain/continuity/structural.ts` (CC-2, CC-5): pure functions over the read model for one chapter or all: a character present in a strand while dead or unborn in that strand's year; a character acting on a fact (facts in play) before the year they learn it; an event linked to the chapter as having happened but dated after the story year; the FT-6 tree warnings; a strand year outside its POV's lifetime. Each finding carries a stable key (check, chapter, strand, entry) and cites both sides. A unit test asserts the fixture yields exactly the findings in `fixtures/expected/structural-findings.json` (S1, S2, S3) and nothing on the clean chapters (CC-5).

2. **Alignment check by Claude** (CC-3): the `alignment` feature takes the chapter text split into numbered lines (paragraph per line, stable numbering stored with the chapter), the entries selected by the M7 selection for that chapter, and the stored plot for it (strands and years, its beats, beats in its arcs dated at or before its story year, chapter order, facts in play) and returns findings, each with: quoted passage with line numbers, the cited entry or beat ID, a plain explanation, a kind (age, date, place, knowledge, beat missing, order, strand year, other), and a prepared change set (a list of field changes to entries, beats, or strands that would make the bible match the chapter). Code validates every cited ID exists and every change set targets real fields (reject and show invalid ones). Scope: one chapter or the whole manuscript, run on demand from the chapter page and the dashboard (CC-1). Model: the alignment setting, default `claude-opus-5-5`. Streaming with Stop.

3. **Resolutions** (CC-4): findings live in a `findings` collection with state open, dismissed, resolved, manuscript-wins, rewrite. **Manuscript wins** shows the change set as a before and after diff and applies all of it through the normal write path in one transaction after a snapshot, recorded in revisions and undoable from the renderer stack. **Rewrite recommended** creates a `rewriteTasks` entry (chapter, line numbers, quoted lines, what must change) with no prose; a static test asserts the rewrite prompt and the task schema have no field for suggested text (AI-4). **Dismiss** stores the finding key plus a hash of the chapter text and the cited entry's revision; a re-run hides a dismissed finding unless either hash changed. The dashboard's Rewrite tasks tile and Check alignment button become live; the chapter page lists its open tasks.

4. **Tests**: unit (structural checks against the fixture with the expected file, dismissal hash logic, change set validation, line numbering stability); integration (whole-manuscript run with the fake Claude returning recorded findings for P1 and P2, manuscript wins applies and is undoable, rewrite task created with no prose, dismissed stays dismissed across a re-run and reappears after editing the entry); e2e (run Check alignment from the dashboard on the fixture, see S1 to S3 and the recorded P1 and P2, resolve one each way); the live smoke test from M6 reports whether the real model finds P1 and P2 (informs, does not gate).
