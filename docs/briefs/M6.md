# M6 brief: Claude panel, tools, proposal queue, import proposals

Criteria: ARCH-4, ARCH-5, AI-1 to AI-7, IM-5. Read first: `docs/ARCHITECTURE.md` (the Claude section is binding: API key from the keychain, per-feature models, read-only in-process MCP tools, `propose_change` only writes proposals, every system prompt forbids prose), `SPEC.md` sections 3, 5.13, 5.16 (IM-5), 5.19, 8 (T-3), amendments A3, A19, A21, A23. Do not read anything under `mockups/`; the panel shows availability states (ready, no key, offline, running, stopped), a proposal queue with before and after, and settings for the key and per-feature models, all styled with the existing token CSS in `src/renderer/src/app.css`. Then the code from M0 to M5. Check the current Agent SDK documentation (https://code.claude.com/docs/en/agent-sdk/typescript.md, mcp.md, permissions.md) before writing SDK code; do not rely on memory for option names.

Deliverables, keeping `npm test` green:

1. **Claude client interface** `src/main/claude/client.ts`: `run(feature, input, { model, signal, onPartial })` returning structured output; `sdk.ts` implements it with `@anthropic-ai/claude-agent-sdk` `query()` (API key from the keychain service `novel-companion-anthropic` passed only in the subprocess environment; `permissionMode: 'dontAsk'`; `allowedTools` limited to the app's own MCP tools; built-in tools disallowed; `maxTurns` bounded; `pathToClaudeCodeExecutable` resolved to the bundled binary and configured for `asarUnpack` in `electron-builder.yml`); `fake.ts` replays recorded responses from `tests/fixtures/claude/*.json` keyed by feature and a hash of the input, and fails plainly on an unknown key so tests never silently pass. Every system prompt lives in `src/main/claude/prompts/` and contains the sentence "Never draft prose for the novel. Produce only the structured output requested." A unit test asserts it for every prompt (AI-4).

2. **Tools** `src/main/claude/tools.ts` as one in-process MCP server: `search_entries`, `get_entry`, `timeline_for_year`, `relatives_of`, `get_chapter` (all read the read model and return JSON with entry IDs; `readOnlyHint`), and `propose_change` (create, change, delete, link) which validates with zod and inserts into the `proposals` collection only (AI-3). A static test asserts no tool imports the repository's write functions except `propose_change`'s insert into proposals.

3. **Question panel** (AI-1, AI-2): available from every screen (a toggle in the frame), streaming output, a stop button backed by an AbortController and the SDK's interrupt, saved conversations in a `conversations` collection, and under each answer the list of entries read (collected from tool calls). The panel's model comes from settings. A recorded "write the scene" request yields the one-sentence refusal with facts and no prose (test with the fake).

4. **Proposal queue** (AI-3, ED-7): a review screen listing proposals with the exact change as a before and after diff against the live entry; Approve applies it through the normal write path (snapshot first if it is a bulk apply), Edit opens the proposed values for change before approval, Reject records the rejection; nothing is written until approval; integration test proves the live value is unchanged before and changed after.

5. **First use, errors, settings** (AI-6, AI-7, ST-1 parts): on the first Claude use per bible a plain notice states that content used by the question panel, session briefs, alignment checks, chapter summaries, and import proposals is sent to Anthropic, with Continue and Not now; failures (no network, bad key, rate limit, model not available) show a plain message with what to do next and never lose typed input or corrupt data (test each with the fake throwing typed errors); settings hold the API key (masked, replace only), the per-feature model selects populated from the live models endpoint with cached fallback and the defaults from DB-4, and the sign-in status check.

6. **Import proposals** (IM-5): on the document import screen an optional "Ask Claude to propose structured entries" sends the imported text as material to analyse, framed in the prompt as data and never as instructions (AI-5), and routes results into the proposal queue; a recorded fixture includes an injected instruction line in the document and the test asserts it is not followed.

7. **Live smoke test** (T-3): `npm run test:live` runs one real call per feature against the API with the fixture, prints the output, and reports whether P1 and P2 from section 7 are found by the alignment check; it informs and does not gate `npm test`.

Constraints: no em dashes; never print or store the key anywhere but the keychain; `fixtures/expected/` untouched; test names start with the criterion ID. Report: `npm test` tail, criterion to test names table, files changed, anything not done with the reason, and the exact SDK option names you used with the doc URL that confirms each.
