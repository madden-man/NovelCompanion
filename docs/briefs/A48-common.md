# A48 common brief: capture routing

Read first, in this order: `SPEC.md` section 5.25 (CR-1 to CR-10) and amendment A48 at the end of section 10, `docs/CAPTURE-ROUTER-2026-10-22.md` (the design and Tommy's decisions), `src/shared/domain/captureRouter/types.ts` (the contract every branch codes against; do not change it without saying so in your report), `docs/ARCHITECTURE.md` (binding: the ten rules, Claude, Capture), `src/main/claude/features/capture.ts` and `src/renderer/src/workspace/capture.tsx` (what capture is today), then the code your own brief lists and the tests that cover it. Do not open anything under `mockups/`.

The goal in Tommy's words (2026-10-22): "design a way to efficiently route any new info added via cmd k to novel companion to the most relevant section so that we can save on anthropic tokens. for example, if an entry were added that said 'chinese people in san francisco begin to say yee haw ironically starting around 2065', that should be added a cultural data piece under the san francisco community." His decisions over the design: Route A files without Claude; a demonym plus a place prefers the place's community; chips appear after Enter, not while typing; multi-sentence lines are split and each sentence is filed on its own route.

The work runs in two waves, each builder on a branch off `main` in its own worktree under `.claude/worktrees/<branch>`. The worktree's `node_modules` is a symlink to the main checkout's; if a build or test fails in a way that smells of that, say so in your report rather than running `npm ci` in the worktree.

Rules that keep the merge clean:

1. Touch only the files you own. If you must change a file another builder owns (a shared type, one wiring line), keep it to the fewest lines, do not reformat around it, and list every such change in your report with the file and the lines. The architect re-applies them at integration. `types.ts` is the contract: if a field is missing, add it at the end of the interface with a comment naming your branch, and say so in the report.
2. `app.css` is shared: append your rules at the end under a comment with your branch name, never edit existing rules. Prefer a CSS file next to your component.
3. No schema change and no migration in A48. Everything new is code and fixtures; the hints that cross IPC are IDs and numbers (AI-4), never text.
4. Tests prove criteria: titles start with the criterion ID (`test('CR-2 "by the 2070s" sets the start and leaves the end open', ...)`). Reuse the fixture bible (`tests/helpers/loadFixture.ts`) and the recorded Claude fake (`fixtures/claude/recordings.json`); never call the real API in tests. Keep every existing test that still describes true behaviour; change a test only where the criterion changed the behaviour, and say which in your report.
5. Running tests on this Mac: `npm run typecheck`, `npx eslint src tests scripts`, `npx prettier --check src tests scripts`, `npm run test:unit`, then only the integration and e2e files you touched, one file at a time (`npx vitest run --project integration tests/integration/x.test.ts`; `npx electron-vite build && npx playwright test tests/e2e/x.spec.ts`). Never run the full `npm test`, never run several Playwright or vitest suites at once: builders share the machine. The architect runs the whole suite at integration. If `mongod` dies with exit 137 or ECONNREFUSED, re-sign the cached binary: `codesign --force -s - ~/.cache/mongodb-binaries/mongod-*`. Every e2e run is hidden (`NOVEL_COMPANION_HIDDEN=1`, set by the helpers); never show the app window, never run the journey or package suites.
6. Known before you start: `tests/e2e/editing.spec.ts` "ED-1 every field of every entity ..." times out on "Add to Strands" on `main` already. The three `a47-*` worktrees beside yours belong to another wave; do not touch them.
7. Copy standards (ARCHITECTURE rule 9): plain words, active voice, no em dashes in any string or comment, labels never muted, both themes, keyboard reachable with visible focus, contrast per NF-2. Name controls for what they do ("File it", "Ask Claude instead", "Review later").
8. Commit on your branch as you go with plain messages; use `git add <paths>`, never `git add -A` (a `node_modules` symlink sits in the worktree); do not merge, rebase, push or stash (`git stash` is forbidden on this machine). Do not change `SPEC.md`, `ARCHITECTURE.md` or `PROGRESS.md`; if a criterion is wrong or impossible, stop and say so in your report. Put what the architect must know for ARCHITECTURE.md in your report instead.
9. Report at the end: the commands you ran with their last lines, a table of criterion to test names, the lines you changed in files you do not own, the tests you changed and why, anything not done with the reason, and the API you built (signatures and a short example) so the next wave can code against it without reading your source.
