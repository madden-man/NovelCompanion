Deliverables, keeping `npm test` green:

1. **Import mapping engine** in `src/shared/domain/import/`: a pure mapping model: a source (file, sheet, shape table or grid), a target section, column-to-field assignments (table) or row-label-to-category and year-column-to-date rules with heading rows feeding the category path (grid); a preview that applies the mapping to the parsed rows and reports per row success or failure with the reason (IM-2); a stable source location string per entry (file, sheet, row and column, or paragraph index) stored in `sourceRef` (IM-6); an identity rule per mapping (which fields identify the same entry across imports) so re-import updates instead of duplicating (IM-3) and produces a change set (new, changed with old and new values, unchanged count) that must be approved per change before anything is written (ED-7); the conflict rule (IM-7): when a field already has a value from a different source or an earlier version of the same source, the newer source (by file modification time or Drive modified time passed in with the source) wins, and an open question is created listing every source with its value and date.

2. **Parsers** in main: `exceljs` for workbooks (sheet list, cell grid with merged cells handled, numbers and dates normalized, years like `2055.0` read as 2055), `mammoth` for `.docx` to HTML with headings, italics, and scene breaks (a paragraph of only `***`, `#`, or three or more spaces or dashes) preserved, then HTML to the body rich-text format the editor uses (IM-4, MS-1 formatting rule).

3. **Import screens**: pick a file; for workbooks a sheet picker, shape toggle, mapping table with a live preview of the first rows, saved mapping per file (keyed by file name and sheet, stored in the bible's `meta`); for documents a kind picker (character backstory, chapter, general note), a target entry picker or new entry, a preview with headings kept; an import run that reports counts and failed rows (IM-2); re-import showing the change set with checkboxes (IM-3); the conflict panel with the open question created (IM-7).

4. **Snapshots** (BK-1, BK-2, BK-4): a complete JSON dump of every collection of the open bible to `app.getPath('userData')/snapshots/<bibleId>/<ISO timestamp>/<collection>.json` plus a `manifest.json` with counts and the schema version; taken daily on first launch of the day, before every import, restore, and bulk change (list rename, apply proposal, apply change set), and on demand; keep the last N (setting, default 30); restore replaces every collection of that bible in one transaction after taking a snapshot first, and fails without changes if the manifest does not validate; writes are single-document or transactional so a forced quit never persists a partial edit (prove with a test that kills the write mid-transaction using a session abort and shows the document unchanged).

5. **JSON export and round trip** (BK-3): export the whole bible (every collection including revisions, lists, meta, settings) to one JSON file; import that file into an empty bible; a test asserts deep equality of every document and setting after the round trip against the loaded fixture.

6. **Tests**: unit for the mapping engine with the fixture workbook (table sheet and grid sheet, a failing row with a non-numeric year, identity re-import, conflict newest wins); integration for import into a real local MongoDB, re-import without duplicates, snapshot and restore, JSON round trip; e2e: import the fixture workbook through the interface with a saved mapping, see the preview, approve a re-import change, take a snapshot, restore it.
