# M1 brief: data model, generic editing, history, undo, trash, links

Criteria: ED-1 to ED-10, T-5. Read first: `docs/ARCHITECTURE.md` (binding), `SPEC.md` sections 2, 4 (every row, with amendments A5 to A9 and A18), 5.1, 8 (T-5), and the mockups `mockups/app-shell.html` (the editing rules demo and inspector are the reference for look and copy; open the file and read the HTML, do not run it). Then read the existing code under `src/` and `tests/` from M0 and build on it; do not rewrite what works.

Deliverables, in this order, keeping `npm test` green:

1. **Schemas for every entity in section 4** in `src/shared/schema/`: Family, Character (names block per CH-2: full name, Chinese characters, romanization, name order, birth name, married name, nicknames, what each other character calls them; birth and death as StoryDate; birthplace; family memberships; backstory; voice notes as a list of year-or-age plus text; places lived with year ranges), Union, ParentLink, Relationship, Book, Part, Arc (owner, scope, year range), Chapter (part, reading order, strands each with label, primary flag, year or range, POV, present characters, places; arcs, themes, facts in play, written flag, manuscript text, summary, source file), PlotBeat (arcs, chapter, year, POV, description, world context, experience note, order), WorldEvent (date or range, real or invented, category path, regions, places, characters, formative), EraState, CulturalEntry, Place (parent, descriptions by year range), GlossaryTerm, Fact, KnowledgeRecord, Theme (appearances), OpenQuestion, SessionLog, CustomSection definition and CustomEntry (CS-1 field kinds: text, long text, number, year, year range, single choice, tags, link). All share the common entry fields. Each schema exports a field manifest (name, kind, label, required, warnings) so a generic editor can render it and T-5 can walk it.

2. **Repository and read model** extended to every collection with indexes; links stored as `{ targetId, kind }` arrays and backlinks derived in the read model (ED-9); revisions on every write (ED-4); soft delete with restore and a `linkedFrom` count before delete (ED-5); editable lists in the `lists` collection (union types, parent-link types, communities, tags, section names, era ranges, families) with a rename operation that updates every entry using the value in one transaction (ED-8); field warnings computed by pure functions in `src/shared/domain/warnings.ts` from the schemas (death before birth, year outside range, and the KN-2 and FT-6 warnings that are purely field-level) and returned with every read, never blocking a write (ED-10).

3. **IPC channels** for list, get, create, update, delete, restore, revisions, revision diff, restore revision, lists get and rename, backlinks, search (reusing M0 search), with zod on both sides.

4. **Renderer**: a generic entry editor driven by the field manifest, with a section list in the rail and an inspector; autosave with a 500 ms debounce and a visible "Saved" state (ED-2); undo and redo stacks of at least 50 commands with Cmd+Z and Shift+Cmd+Z, covering field edits, creates, deletes, restores, link edits (ED-3); a revision history drawer that lists revisions, shows a side by side diff of any revision against current, and restores one (ED-4); a trash view with restore (ED-5); `@` in any long-text field opens a search picker that inserts a link, and every entry shows "Linked from" (ED-9); warnings shown at the field with plain text (ED-10); list management screen with rename (ED-8). Use the token CSS already in `src/renderer/src/theme.css`; copy standards: plain, active voice, no em dashes, labels in text tokens.

5. **Tests**: unit tests for warnings, field manifests, undo stack logic, list rename cascade logic; integration tests for every repository operation per collection, revisions, trash, backlinks, list rename cascade; **T-5**: an automated test that reads every schema's field manifest, creates one entry per entity, sets every field to a new value through the IPC layer (not the repository directly), restarts the app (close and relaunch the Electron app in e2e, or at minimum reopen the bible from a fresh process in integration), and asserts every value persisted. A field with no coverage fails the test by construction (iterate the manifest; the test must not enumerate fields by hand). ED-6 is satisfied by generated-content fields (summary, brief, findings) being ordinary fields in the manifest. ED-7 needs only the mechanism now: a `proposals` collection and an `applyProposal` write path that records the approval; the UI for it comes in M6.

Also fix from the M0 review: close the `MongoClient` when `connect()` throws (`src/main/db/connection.ts`, `src/main/ipc/handlers.ts`); make the e2e `MongoMemoryServer` a replica set (`MongoMemoryReplSet`) because the write path uses transactions; add unit cases for the `bible.create`, `bible.open`, `bible.current` schemas in `tests/unit/ipc-contract.test.ts`.

Constraints: no em dashes anywhere; `fixtures/expected/` untouched; pure logic in `src/shared/domain/` with no Electron, MongoDB, or React imports; test names start with the criterion ID. Report at the end: `npm test` tail, a table of criterion to test names, and anything not done with the reason.
