# A47 common brief: everything on screen is a field

Read first, in this order: `SPEC.md` section 5.24 (IP-1 to IP-18) and amendment A47 at the end of section 10, `docs/EDIT-AUDIT-2026-10-22.md` (the audit the criteria came from: every value each screen shows, how it is edited today, with file and line at commit 3671b2b), `docs/ARCHITECTURE.md` (binding: the ten rules, Claude, the app shell), `src/renderer/src/workspace/undo.tsx` and `src/shared/domain/undoRunner.ts` (how a step is recorded and replayed), then the code your own brief lists and the tests that cover it. Do not open anything under `mockups/`; your brief describes what you build.

The goal in Tommy's words (2026-10-22): "implement the suggestions, creatively handling each page in such a way that it's both editable and usable during writing sessions." Both halves matter. Every value a screen shows must be a field, and the screen must stay a reading surface while he writes: a field looks like text until picked, opening it moves nothing, covers nothing, scrolls nothing, and closing it leaves the page as it was. When the two pull against each other, the reading surface wins and the edit path moves to a popover anchored to the text, never a dialog.

The work runs in three waves of three builders, each on a branch off `main` in its own worktree under `.claude/worktrees/<branch>`. The worktree's `node_modules` is a symlink to the main checkout's; if a build or test fails in a way that smells of that, say so in your report rather than running `npm ci` in the worktree.

Rules that keep the merge clean:

1. Touch only the files you own. If you must change a file another builder owns (a shared type, a CSS token, one wiring line), keep it to the fewest lines, do not reformat around it, and list every such change in your report with the file and the lines. The architect re-applies them at integration. `repository.ts` and `ipc.ts` are shared between `a47-model` and `a47-guard`: add your methods and channels in their own block under a comment with your branch name, at the end of the file or the end of the channel map, and never edit each other's.
2. `app.css` is shared: append your rules at the end under a comment with your branch name, never edit existing rules. Prefer a CSS file next to your component.
3. The data must survive. Any schema change ships with a migration that takes a snapshot first (see `session.ts` and migration 9 and 10 for the pattern), is idempotent, and has an integration test that runs it on the fixture and on a copy at the previous version. The schema version bumps once, to 11, in `a47-model`; `a47-guard` adds no migration (its data lives in `meta` documents created on first write).
4. Tests prove criteria: titles start with the criterion ID (`test('IP-1 a year field saves on Enter as one undo step', ...)`). Reuse the fixture bible (`tests/helpers/loadFixture.ts`) and the recorded Claude fake (`fixtures/claude/recordings.json`); never call the real API in tests. Keep every existing test that still describes true behaviour; change a test only where the criterion changed the behaviour, and say which in your report.
5. Running tests on this Mac: `npm run typecheck`, `npx eslint src tests scripts`, `npx prettier --check src tests scripts`, `npm run test:unit`, then only the integration and e2e files you touched, one file at a time (`npx vitest run --project integration tests/integration/x.test.ts`; `npx electron-vite build && npx playwright test tests/e2e/x.spec.ts`). Never run the full `npm test`, never run several Playwright or vitest suites at once: three builders share the machine. The architect runs the whole suite at integration. If `mongod` dies with exit 137 or ECONNREFUSED, re-sign the cached binary: `codesign --force -s - ~/.cache/mongodb-binaries/mongod-*`. Every e2e run is hidden (`NOVEL_COMPANION_HIDDEN=1`, set by the helpers); never show the app window, never run the journey or package suites.
6. Known before you start: `tests/e2e/editing.spec.ts` "ED-1 every field of every entity ..." times out on "Add to Strands" on `main` already. Do not spend time on it unless your change is the cause of a new failure in it.
7. Copy standards (ARCHITECTURE rule 9): plain words, active voice, no em dashes in any string or comment, labels never muted, both themes, keyboard reachable with visible focus, contrast per NF-2. Name controls for what they do ("Add an event in 2045", not "New").
8. Commit on your branch as you go with plain messages; use `git add <paths>`, never `git add -A` (a `node_modules` symlink sits in the worktree); do not merge, rebase, push or stash (`git stash` is forbidden on this machine). Do not change `SPEC.md`, `ARCHITECTURE.md` or `PROGRESS.md`; if a criterion is wrong or impossible, stop and say so in your report. Put what the architect must know for ARCHITECTURE.md in your report instead.
9. Report at the end: the commands you ran with their last lines, a table of criterion to test names, the lines you changed in files you do not own, the tests you changed and why, anything not done with the reason, and the API you built (signatures and a short example) so the next wave can code against it without reading your source.
