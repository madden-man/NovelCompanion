# Architecture decisions

Binding for every builder. `SPEC.md` says what; this file says how. Change it only through the architect.

## Repository layout

```
src/
  main/            Electron main process: db, readmodel, search, ipc handlers, claude, drive, import, snapshots
  preload/         contextBridge exposing `window.api` only
  renderer/        React app
  shared/          zod schemas, IPC contract types, pure domain logic (ages, tree, selection, checks)
fixtures/
  novel/           the fixture novel from SPEC section 7 as JSON, one file per collection
  expected/        hand-written expected answers (never generated by code under test)
  files/           fixture .xlsx and .docx for import tests
tests/
  unit/            pure logic, no database
  integration/     real local MongoDB with the fixture loaded
  e2e/             Playwright against the built app
  live/            on-demand real Claude smoke test
mockups/           approved interactive mockups (reference for UI and copy)
docs/              this file, findings, progress
```

## Rules every builder follows

1. **Pure domain logic lives in `src/shared/domain/`** and has no Electron, MongoDB, or React imports. Ages, alive-or-dead, tree validation, brief selection, structural continuity checks, romanization checks, and import mapping are pure functions over plain objects. Unit tests cover them directly.
2. **One write path.** Every mutation goes through `src/main/db/repository.ts`: validate with zod, write to MongoDB (single document, or a transaction for multi-document changes), append a revision, update the read model, patch the search index, emit a change event to the renderer. No handler writes to a collection directly.
3. **Renderer has no network and no secrets.** It talks to main only through the typed `window.api` exposed by preload. The IPC contract is in `src/shared/ipc.ts`: every channel has a zod request and response schema, and the preload validates both.
4. **IDs** are ULIDs as strings in `_id`. Links between entries are stored as `{ targetId, kind }` arrays on the source entry; backlinks are derived in the read model.
5. **Trash and revisions.** Delete sets `deletedAt`; restore clears it. Every write appends to `revisions` with the full prior document. Undo and redo are renderer-side command stacks that replay inverse writes through the same write path.
6. **Dates.** A `StoryDate` is `{ year: number, month?: number, day?: number }` or `{ unknown: true }`. Ages use the rules in TL-3 and TL-4 exactly.
7. **Status and provenance** fields exist on every entry; the fixture and tests assert they survive import and export.
8. **No telemetry, no analytics, no crash reporters.** ARCH-7.
9. **Copy standards.** Plain copy, active voice, no em dashes in any string, labels never in muted grey, both themes designed, keyboard reachable. The mockups are the reference.
10. **Tests prove criteria.** Each test names the criterion it covers in its title, for example `test('TL-4 dying year is listed as alive and flagged', ...)`. A reviewer maps criteria to tests from those names.

## Claude

**Auth decided (2026-10-10, A23): API key.** Stored in the macOS keychain, service `novel-companion-anthropic`, account `novel-companion`; the main process reads it with `@napi-rs/keyring` and passes it to the SDK as `ANTHROPIC_API_KEY` in the subprocess environment only. Never logged, never in a file, never sent to the renderer beyond a masked suffix. Verified against `GET /v1/models` on 2026-10-10; the live list included `claude-opus-5-5`, `claude-fable-5-1`, `claude-sonnet-5-5`, `claude-haiku-5-5`. Settings populate the model selects from that endpoint, cached, with the defaults from DB-4.

Verified SDK facts (same docs): package `@anthropic-ai/claude-agent-sdk`; `query({ prompt, options })` is an async generator of messages; `options.systemPrompt`, `options.allowedTools`, `options.disallowedTools`, `options.permissionMode: 'dontAsk'`, `options.mcpServers`, `options.model`, `options.maxTurns`; stop with the query object's `interrupt()` and `close()`; in-process tools through `tool(name, description, zodShape, handler, { annotations: { readOnlyHint: true } })` and `createSdkMcpServer({ name, tools })`, allowed as `mcp__<server>__<tool>`; the npm package bundles the Claude Code binary as an optional dependency and `options.pathToClaudeCodeExecutable` overrides where to find it (needed when packaged in asar: unpack the SDK with electron-builder `asarUnpack`). Model IDs for the settings list come from Anthropic's current model page at M6, not from memory; the environment reports `claude-fable-5-1`, `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-4-5-20251001`.

- The question panel (A21) is a fifth Claude feature: a conversation with read-only in-process MCP tools (search entries, get entry, timeline for a year, relatives, get chapter) and `propose_change`; its system prompt forbids prose and instructs a one-sentence refusal. The other four features: session briefs, continuity prose checks, chapter summaries, import proposals. Each is a function in `src/main/claude/features/` that takes a deterministic input (the manifest contents, the chapter text plus its selected entries, the chapter text, or the imported document) and returns structured output validated with zod.
- Each feature calls the Agent SDK `query()` with `permissionMode: 'dontAsk'`, no built-in tools (`allowedTools` limited to the app's own `mcp__bible__*` tools, `disallowedTools` covering Bash, Edit, Write, WebFetch, WebSearch). The four structured features get all their material in the prompt and only the `propose_change` tool (import proposals and alignment findings) or no tool at all (briefs, summaries). The panel gets the read-only tools plus `propose_change`. `propose_change` writes only to the `proposals` collection (AI-3).
- Every system prompt contains the sentence "Never draft prose for the novel. Produce only the structured output requested." A unit test asserts it is present in every feature prompt, and a static test asserts no renderer channel sends free-form user text to any Claude feature (AI-4).
- Streaming partial messages feed the feature's output pane; an AbortController backs the Stop button.
- The model is read from settings per feature (DB-4): briefs default `claude-opus-5-5`, the others default `claude-sonnet-5-5`.
- In the test suite the SDK is replaced by a recorded-response fake behind the same interface (`src/main/claude/client.ts` exports an interface; `fake.ts` and `sdk.ts` implement it).
- If the key is unset or rejected, the app says so and opens the settings screen.

## Fixture novel

`fixtures/novel/` holds the Hale and Zhou families from SPEC section 7 exactly, including the planted errors S1, S2, S3, P1, P2, the two-strand chapter, categories, and the grid-shaped workbook. `fixtures/expected/` holds the TL-2 known answers and the expected structural findings as hand-written JSON. Tests load the fixture into a fresh local MongoDB per file.

## Builder workflow

A builder gets the milestone's criteria, this file, and the files it may touch. It writes code and tests, runs `npm test` until green, and reports which tests cover which criteria. The architect runs `npm test` again and then sends the spec and the code (not the builder's report) to a fresh reviewer.
