## Rules every builder follows

1. **Pure domain logic lives in `src/shared/domain/`** and has no Electron, MongoDB, or React imports. Ages, alive-or-dead, tree validation, the selection, structural continuity checks, romanization checks, and Word document parsing are pure functions over plain objects. Unit tests cover them directly.
2. **One write path.** Every mutation goes through `src/main/db/repository.ts`: validate with zod, write to MongoDB (single document, or a transaction for multi-document changes), update the read model, patch the search index, emit a change event to the renderer. No handler writes to a collection directly. The exceptions are structural, not entry writes: `src/main/db/bibles.ts` (the `bibles` registry, migrations, and dropping a bible), `backupHandlers.ts` (dropping a half-made bible when a bible file fails to load), `src/main/backup/dump.ts` (the restore transaction that replaces every collection), and `src/main/claude/store.ts` (the `conversations` collection, one turn at a time).
3. **Renderer has no network and no secrets.** It talks to main only through the typed `window.api` exposed by preload. The IPC contract is in `src/shared/ipc.ts`: every channel has a zod request and response schema, and the preload validates both.
4. **IDs** are ULIDs as strings in `_id`. Entries refer to each other only through reference fields named in the manifests; the read model derives who refers to an entry (`ReadModel.backlinks`) for usage counts and the missing-target warning (A52).
5. **Trash.** Delete sets `deletedAt`; restore clears it. Undo and redo are renderer-side command stacks that replay inverse writes through the same write path. Only entries (the collections in `entrySchemas`) carry `deletedAt`. The bible's `meta`, `lists`, `proposals`, `conversations` and `sceneOutlineVersions` collections are not entries and carry none of it. Migration 13 dropped `revisions`, `importSources`, `briefs`, `sessionLogs` and `books`, and the `meta` documents `importMappings` and `drive` (A52, A53).
6. **Dates.** A `StoryDate` is `{ year: number, month?: number, day?: number }` or `{ unknown: true }`. Ages use the rules in TL-3 and TL-4 exactly.
7. Withdrawn by A52 (status and provenance are gone).
8. **No telemetry, no analytics, no crash reporters.** ARCH-7.
9. **Copy standards.** Plain copy, active voice, no em dashes in any string, labels never in muted grey, both themes designed, keyboard reachable. The mockups are the reference.
10. **Tests prove criteria.** Each test names the criterion it covers in its title, for example `test('TL-4 dying year is listed as alive and flagged', ...)`. A reviewer maps criteria to tests from those names. The fixture tests are the one exception: they cover SPEC section 7, not a numbered criterion, so their titles start with "Section 7" (17 titles in `tests/unit/fixture.test.ts` and `tests/integration/fixture.test.ts`).

Never logged, never in a file, never sent to the renderer beyond a masked suffix. Verified against `GET /v1/models` on 2026-10-10; the live list included `claude-opus-5-5`, `claude-fable-5-1`, `claude-sonnet-5-5`, `claude-haiku-5-5`. Settings populate the model selects from that endpoint, cached, with the defaults from DB-4.

Verified SDK facts (same docs): package `@anthropic-ai/claude-agent-sdk`; `query({ prompt, options })` is an async generator of messages; `options.systemPrompt`, `options.allowedTools`, `options.disallowedTools`, `options.permissionMode: 'dontAsk'`, `options.mcpServers`, `options.model`, `options.maxTurns`; stop with the query object's `interrupt()` and `close()`; in-process tools through `tool(name, description, zodShape, handler, { annotations: { readOnlyHint: true } })` and `createSdkMcpServer({ name, tools })`, allowed as `mcp__<server>__<tool>`; the npm package bundles the Claude Code binary as an optional dependency and `options.pathToClaudeCodeExecutable` overrides where to find it (needed when packaged in asar: unpack the SDK with electron-builder `asarUnpack`). Model IDs for the settings list come from Anthropic's current model page at M6, not from memory; the live list on 2026-10-10 reported `claude-fable-5-1`, `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`. The Haiku ID is `claude-haiku-5-5` everywhere (`KNOWN_MODELS` in `src/shared/claude.ts`).

- The question panel (A21) is a fifth Claude feature: a conversation with read-only in-process MCP tools (search entries, get entry, timeline for a year, relatives, get chapter) and `propose_change`; its system prompt forbids prose and instructs a one-sentence refusal. The other features: continuity prose checks, chapter summaries, capture and the fast file (`captureFast`); briefs and import proposals went with A53. Each is a function in `src/main/claude/features/` that takes a deterministic input (the chapter text plus its selected entries, the chapter text, or the capture text and its routing) and returns structured output validated with zod.
- Each feature calls the Agent SDK `query()` with `permissionMode: 'dontAsk'`, no built-in tools (`allowedTools` limited to the app's own `mcp__bible__*` tools, `disallowedTools` covering Bash, Edit, Write, WebFetch, WebSearch). Summaries, alignment and the fast file get all their material in the prompt and no tool; capture gets the read tools and `propose_change` (below). Alignment findings come back as structured output and code stores the prepared change set on the finding itself; nothing reaches the `proposals` collection. The panel gets the read-only tools plus `propose_change`. `propose_change` writes only to the `proposals` collection (AI-3).
- Every system prompt contains the sentence "Never draft prose for the novel. Produce only the structured output requested." A unit test asserts it is present in every feature prompt, and a static test asserts that only the question panel and the capture box (KB-6, as material) send free-form user text to a Claude feature (AI-4).
- Streaming partial messages feed the feature's output pane; an AbortController backs the Stop button.
- The model is read from settings per feature (DB-4): alignment checks (CC-3) default `claude-opus-5-5`; chapter summaries, capture and the question panel default `claude-sonnet-5-5`; the fast file defaults `claude-haiku-5-5` (`DEFAULT_MODELS` in `src/shared/claude.ts`). `read()` in `src/main/claude/settings.ts` drops a model saved for a feature the app no longer has, and the run store skips a saved run of one (A53).
- In the test suite the SDK is replaced by a recorded-response fake behind the same interface (`src/main/claude/client.ts` exports an interface; `fake.ts` and `sdk.ts` implement it).
- If the key is unset or rejected, the app says so and opens the settings screen.

### Capture (M11, KB-6, KB-7)

`features/capture.ts` is the one feature that uses the panel's tools inside a structured run: `FeatureDefinition` gained an optional `tools?(input, session, sink)` so a feature can hand Claude the AI-2 read tools plus `propose_change`; features that declare none still get no tools. The renderer's `capture.tsx` (Cmd+K, the status bar Add button) starts `claude.capture` (a write channel: the run is saved to the bible) with the text as material (AI-5), the story time and the chapter being written. Proposals stream into the box as `ED-7` diffs (`ProposalDiff`, exported from `review.tsx`); "File it" approves the ticked ones through the existing approve path and rejects the rest, recorded as one undo step from the existing command types (ED-3). Without a key, offline, or when the run fails before proposing anything, the text is written as an open question (KB-7); since A52 a capture sets no status, source note or tag. Recordings for the fixture bible are appended to `fixtures/claude/recordings.json` (match on the capture text).

### Capture routing, A48 (2026-10-22, CR-1 to CR-10)

A Cmd+K line is routed before anything is sent. `src/shared/domain/captureRouter/` is a pure router (rule 1): `buildIndex` turns the bible's lists and live entries into a `RouterIndex` (characters with full, first and Chinese names, places with their community and parent, communities with the lexicon's aliases and country words, categories with cue words, age groups, cultural lines, moments, glossary), and `routeCapture(text, index, { storyYear, povCommunityId, hints })` splits the text into sentences, parses years (CR-2), resolves names (CR-3), scores sections by weighted cues (CR-4), builds drafts in main's `ProposalDraft` shape, and decides a route per fact (CR-5): `local` (filed from the box, no Claude), `fast` (one Haiku call, no tools), `full` (today's capture). The lexicon (`lexicon.ts`) is one typed object: cues with weights and plain labels under 50 characters, community aliases keyed by list item ID (East Winds words such as "the city" and "church" are in it on purpose), category cue words, age-group words, year words, a list of English words that stops a first name such as Mark or Dawn matching in lowercase. The design and the measured costs are in `docs/CAPTURE-ROUTER-2026-10-22.md`; the twelve-line fixture in `fixtures/capture/` is the routing's acceptance test, with `briefSaid` where the router's answer was judged better than the design's.

The renderer and main build the same index and run the same router. Only `CaptureHint[]` crosses IPC on `claude.capture` (IDs, numbers and a route per fact, never text, AI-4); main reruns the router with the hints (`features/captureIndex.ts`) and dispatches: facts on `local` are skipped, every `fast` fact goes to `captureFast` in one run, every `full` fact to `capture` in one run. When both are needed the runs are `<runId>-fast` and `<runId>-full` (each at most 64 characters), the handler remembers the pair so `claude.stop` on the box's ID stops both, and a failure to start the second stops the first. A capture of more than 50 facts is refused in plain words. Only local facts gives `started: false` and no run.

`features/captureFast.ts` (CR-7) is the sixth feature: no tools, `maxTurns` 2, default model `claude-haiku-5-5` (the live list on 2026-10-22 had both `claude-haiku-5-5` and `claude-haiku-4-5-20251001`), a structured output of proposals with `fields` as JSON text (an open object cannot be a strict schema), a per-fact `cannotPlace` array, the same `ProposalDraft` validation and `prepareCaptureDraft` as capture, a delete refused, and a change to a text or array field of an existing entry refused (Claude saw only titles of nearby entries). The prompt per fact: story year and capture date, the section and its share, the sentence as material, the candidates with IDs, the section's manifest fields, the list items they take, the 30 nearest titles by year (the community's lines, the character's moments, the top-level categories plus a matched subtree, or the last ten glossary terms), the router's drafts and reasons, all as material (AI-5).

Route C (CR-8): `CaptureInput.routing` holds the full-route facts; the lists are trimmed (communities and regions always, event categories only when a world event scored, languages only for a glossary term, everything when nothing scored), a candidates block per fact tells Claude to skip `search_entries` for them, and the capture run's `get_entry` returns the whole entry with `body` and `backstory` cut at 2,400 characters (never inside a character, a tag or an entity); a proposal that replaces a cut field is refused with a plain reason. The system prompt and tool definitions are identical for every capture, so they are a stable prefix.

Caching, verified in the SDK's bundled binary: prompt caching is on by default and only `DISABLE_PROMPT_CACHING*` environment variables turn it off (`subprocessEnv` never sets them); the request is tools, then system prompt, then messages, with cache breakpoints, so later tool turns of one capture reread the prefix from cache, and captures under five minutes apart share it. The fast file makes one call under the cache minimum, so it does not cache; it is small instead.

The box (CR-6, CR-9), `capture.tsx` with `captureChips.tsx` and `captureLocal.ts`: phases `edit`, `routed`, `filed`, `saved` (`data-phase` reads `running` while a send answers, a run streams or diffs load). Enter reads the five collections, every list and the timeline end fresh over IPC (`loadCaptureBible`: six calls, seven with a chapter picked; every live entry crosses IPC on each Enter, so a lean `capture.index` read on main is the first thing to add if a bible of thousands of entries makes Enter slow), builds the same index main builds (the CR-1 integration row asserts the two are equal), refuses more than 50 sentences with main's words, and shows one card per fact: Route A cards with chips (`Editable` fields with the new `quiet` prop, so no tick and no "Saved" while nothing is stored) and the drafts as a diff; facts for Claude go at once with hints (`sendHints`: kept and already-sent facts carry `route: 'local'`, a sent fact its chip values and route; typed names stay in the box), each run followed by a `RunWatch` mounted outside the dialog so runs land while the box is closed. Every fact has a stand (`standOf`): `question` (saved under KB-7 because there was no key), `sent`, `local` or `unsent`; a run that failed, was stopped empty or could not place the fact puts it back as unsent with Send to Claude and Ask Claude instead, and Escape, Close, Decline and File it put unfiled sentences back in the text field, so no sentence is dropped unless the writer unticks a Route A card. File it calls `fileLocalDrafts` (new list items first, minted IDs put where drafts name a `ref`, an item the list already holds reused), then `fileCapture` for the ticked proposals, then `mergeFilings` into one undo step (approved proposals undone first, then local entries, then new items; `mintedItemCommand` leaves an item in place when another live entry uses it by then). Alt+Enter sends every fact on Route C; with no key the Route A facts still file and the rest is one open question.

## Claude runtime (built in M6)

Every Claude call goes through `ClaudeRuntime` in `src/main/claude/runtime.ts`. It reads the key (`keys.ts`, keychain service `novel-companion-anthropic`) and the model for the feature (`settings.ts`, a JSON file `claude-settings.json` in the app's data folder holding models and the per-bible AI-6 confirmation, never a secret), refuses to send anything before the disclosure is confirmed for the open bible, saves the input before sending, streams, stops, validates, queues proposals, and saves the outcome. A failure writes nothing to the bible and keeps the input (AI-7).

```ts
// src/main/claude/runtime.ts
interface FeatureDefinition<I, O> {
  feature: 'alignment' | 'summaries' | 'capture' | 'captureFast'; // Exclude<ClaudeFeature, 'panel'>
  instructions: string;                 // feature text; systemPrompt() prepends the shared rules and the AI-4 sentence
  input: z.ZodType<I>;                  // the deterministic input, validated first
  output: z.ZodType<O>;                 // structured output; sent as outputFormat json_schema, validated with zod
  title(input: I, session: OpenBible): string;
  build(input: I, session: OpenBible): { prompt: string; given: EntryRefWire[] }; // deterministic
  proposals?(output: O, input: I, session: OpenBible): (ProposalDraft | { summary: string; problem: string })[];
  maxTurns?: number;
}
runtime.runFeature(session, def, rawInput, runId): Promise<{ runId; conversationId; done: Promise<ClaudeRun> }>
runtime.ask(session, { runId, conversationId, question })   // the question panel
runtime.stop(runId)
```

- **Adding a feature (M7 summaries, M8 alignment, M11 capture, A48 the fast file).** Write `src/main/claude/features/<name>.ts` exporting a `FeatureDefinition`, add it to `FEATURES` in `features/index.ts` (the AI-4 test walks that list), and add one IPC channel to `claudeContract` in `src/shared/claude.ts` whose request carries IDs only (a renderer-picked `runId` plus the IDs of the material) and whose handler in `src/main/claude/handlers.ts` calls `runtime.runFeature`. Put any manuscript or imported text in the prompt through `material(label, text)` (AI-5). Return proposals as `ProposalDraft`s; the runtime checks each against the schema and the read model and queues it with `Repository.propose` (source `claude`), and reports any it refused.
- **Runs are saved** in the bible's `conversations` collection (schema version 7, index `{ modifiedAt: -1 }`) by `store.ts`, the one place that writes it. A panel conversation is one document with many turns; a feature run is one document with one turn, its `input`, and its validated `output`. Each turn records the model, status (`running`, `done`, `stopped`, `failed`), the error kind and message, the entries read or given (AI-2), and the proposal IDs. Saves write one turn at a time (`$push` a new turn, `$set` the matching turn), never the whole document. A conversation takes one running turn at a time; a second question while one streams is refused. `runtime.stopAll()` runs when the open bible changes and before the store closes on quit, and waits until each run is saved as stopped. A save that fails mid-run still ends the run with one `finished` event (`saveFailed`); `done` never rejects.
- **Streaming** goes to the renderer as `claude.stream` events (`text`, `read`, `proposal`, `finished`) keyed by the `runId` the renderer chose, so it listens before the run starts. `useRunStream(runId)` in `src/renderer/src/workspace/claude.tsx` follows one run; `ClaudeErrorNote`, `EntriesRead`, and `ProposalsNote` render its state.
- **Tools** (`tools.ts`): `search_entries`, `get_entry`, `timeline_for_year`, `relatives_of`, `get_chapter` read the read model through the shared domain functions; `propose_change` writes a proposal only. A static unit test holds `tools.ts` to that.
- **Client** (`client.ts`): `ClaudeClient.run(request, signal)` yields `text`, `toolCall`, and one `result`, or throws a typed `ClaudeFailure`. `sdk.ts` implements it with `query()` (`tools: []`, `allowedTools` of `mcp__bible__*`, `disallowedTools` of every built-in, `permissionMode: 'dontAsk'`, `settingSources: []`, `persistSession: false`, `includePartialMessages: true`, `outputFormat` for features, an `env` built from nothing with the key and telemetry off, `CLAUDE_CONFIG_DIR` in the app's data folder). `fake.ts` replays `fixtures/claude/recordings.json` (matched by feature and prompt text, running the real tools) and fails plainly on a request it has no recording for. End-to-end runs set `NOVEL_COMPANION_TEST_CLAUDE=1` (honoured outside a packaged app, and in one only under the test exception in "Local development") for the fake, a key held in memory, and a fake models list.

## Local development

- `npm run dev` runs against Atlas with the keychain connection string.
- To run against a throwaway local database instead, start a one-node replica set (the repository uses transactions; a plain `mongod` will not do), for example `MongoMemoryReplSet` from `mongodb-memory-server` with a fixed port and `dbPath`, and run `NOVEL_COMPANION_TEST_MONGODB_URI='mongodb://127.0.0.1:<port>/?replicaSet=testset' NOVEL_COMPANION_USER_DATA=<dir> npm run dev`. The variable is honoured only for a localhost address in an unpackaged build, and the keychain is not read. A packaged build ignores it unless `NOVEL_COMPANION_ALLOW_TEST_URI=1` is also set; that flag exists only for the packaged smoke test and the journey (M10, T-4) and is never set in normal use. When the test database is honoured (`testDatabaseHonoured()` in `src/main/secrets.ts`), the data folder comes from `NOVEL_COMPANION_USER_DATA` and the Claude key is held in memory, so a test run never touches the keychain or the real data folder. With the flag and a local test address (`testSeamsHonoured()`), a packaged build also honours the recorded Claude (`NOVEL_COMPANION_TEST_CLAUDE`, with `NOVEL_COMPANION_TEST_CLAUDE_RECORDINGS` naming the file, since the package holds no fixtures), and the file pickers (`NOVEL_COMPANION_TEST_PICK_*`, `_SAVE_PATH`, `_BIBLE_FILE`); without them it refuses all of these. The proposal seam (`test.propose`) is refused by every packaged build. `npm run test:journey` drives the packaged app in `release/`; `scripts/ensure-package.ts` runs `npm run package` first when it is missing or older than the source.
- **Test runs.** `tests/helpers/testMongo.ts` starts the one local replica set each suite uses (wiredTiger, idle file handles closed quickly so a full run never hits ENFILE). On macOS its data lives on a RAM disk made with `hdiutil` and removed at the end (one left by a killed run is removed by the next); every collection MongoDB creates is fsynced, which costs about 35 ms on the disk and 5 ms in RAM. `NC_TEST_RAM_DISK=0` keeps it on disk. Integration files run on four workers against the one `novel_companion` database, kept apart by fresh bible IDs. The end-to-end run starts the server once in `tests/e2e/globalSetup.ts` (a single-file run, `npx playwright test tests/e2e/x.spec.ts`, too) and each spec file gets its own database on it: `fileDb()` in `tests/e2e/helpers.ts` names it from the file (`tree.spec.ts` is `e2e_tree`), and `launch(db)` passes it to the app as `NOVEL_COMPANION_TEST_DB_NAME`. That variable replaces `novel_companion` for that process only under the conditions of the test address (`testDatabaseName()` in `src/main/secrets.ts`: a local test address, in an unpackaged build or with the allow flag), so the one `.db()` call in `connect()` selects `novel_companion` everywhere else (ARCH-8). Spec files run on three workers (two below eight cores), the tests inside a file in order; every launch has its own data folder, and pickers and exports use per-file temp folders. `offline.spec.ts` starts servers of its own, since it stops them. `npm run test:e2e` runs `electron-vite build` only when something under `src/` (or the build config) is newer than `out/` (`scripts/build-if-stale.ts`); `npm run test:e2e:force` always builds. Every run that drives the app, end-to-end, package smoke and journey, launches it hidden (`NOVEL_COMPANION_HIDDEN=1`, set by `launch()` in `tests/e2e/helpers.ts` and by the direct launches): no dock icon, accessory activation policy, offscreen rendering, so a test run never takes the focus from the person at the keyboard. This is the rule, not an option; `NOVEL_COMPANION_E2E_SHOW=1` is the one way to watch a run. The packaged app honours the flag only together with `NOVEL_COMPANION_ALLOW_TEST_URI=1`.
- If `npm run dev` fails with "Electron uninstall", the Electron binary was not downloaded by `npm install`; run `node node_modules/electron/install.js`.
- Bulk data work on a real bible goes through `Repository` (validation, the own-ancestor check), never raw driver writes, and starts with a manual snapshot so Backups can restore it. Rehearse against a local copy of `novel_companion` first.

## Builder workflow

M8 and M10 are being built now, as Opus sub agents, under this protocol (A32; A30 is withdrawn). M10 is split into settings and offline, performance and accessibility and errors, and packaging and journey. The final audit runs after M8 merges.

A builder gets the milestone's criteria, this file, and the files it may touch. It writes code and tests, runs `npm test` until green, and reports which tests cover which criteria.
