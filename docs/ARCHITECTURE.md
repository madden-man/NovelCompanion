## Rules every builder follows

1. **Pure domain logic lives in `src/shared/domain/`** and has no Electron, MongoDB, or React imports. Ages, alive-or-dead, tree validation, brief selection, structural continuity checks, romanization checks, and import mapping are pure functions over plain objects. Unit tests cover them directly.
2. **One write path.** Every mutation goes through `src/main/db/repository.ts`: validate with zod, write to MongoDB (single document, or a transaction for multi-document changes), append a revision, update the read model, patch the search index, emit a change event to the renderer. No handler writes to a collection directly. The exceptions are structural, not entry writes: `src/main/db/bibles.ts` (the `bibles` registry, migrations, and dropping a bible), `importHandlers.ts` (dropping a half-made bible when a bible file fails to load), `src/main/backup/dump.ts` (the restore transaction that replaces every collection), and `src/main/claude/store.ts` (the `conversations` collection, one turn at a time).
3. **Renderer has no network and no secrets.** It talks to main only through the typed `window.api` exposed by preload. The IPC contract is in `src/shared/ipc.ts`: every channel has a zod request and response schema, and the preload validates both.
4. **IDs** are ULIDs as strings in `_id`. Links between entries are stored as `{ targetId, kind }` arrays on the source entry; backlinks are derived in the read model.
5. **Trash and revisions.** Delete sets `deletedAt`; restore clears it. Every write appends to `revisions` with the full prior document. Undo and redo are renderer-side command stacks that replay inverse writes through the same write path. Only entries (the collections in `entrySchemas`) carry `deletedAt`, status, provenance, and revisions. The bible's `meta`, `lists`, `proposals`, `importSources`, `conversations`, and `revisions` collections are not entries and carry none of them.
6. **Dates.** A `StoryDate` is `{ year: number, month?: number, day?: number }` or `{ unknown: true }`. Ages use the rules in TL-3 and TL-4 exactly.
7. **Status and provenance** fields exist on every entry (see rule 5 for what is not an entry); the fixture and tests assert they survive import and export.
8. **No telemetry, no analytics, no crash reporters.** ARCH-7.
9. **Copy standards.** Plain copy, active voice, no em dashes in any string, labels never in muted grey, both themes designed, keyboard reachable. The mockups are the reference.
10. **Tests prove criteria.** Each test names the criterion it covers in its title, for example `test('TL-4 dying year is listed as alive and flagged', ...)`. A reviewer maps criteria to tests from those names. The fixture tests are the one exception: they cover SPEC section 7, not a numbered criterion, so their titles start with "Section 7" (19 titles in `tests/unit/fixture.test.ts` and `tests/integration/fixture.test.ts`).

## Claude

**Auth decided (2026-10-10, A23): API key.** Stored in the macOS keychain, service `novel-companion-anthropic`, account `novel-companion`; the main process reads it with `@napi-rs/keyring` and passes it to the SDK as `ANTHROPIC_API_KEY` in the subprocess environment only. Never logged, never in a file, never sent to the renderer beyond a masked suffix. Verified against `GET /v1/models` on 2026-10-10; the live list included `claude-opus-5-5`, `claude-fable-5-1`, `claude-sonnet-5-5`, `claude-haiku-5-5`. Settings populate the model selects from that endpoint, cached, with the defaults from DB-4.

Verified SDK facts (same docs): package `@anthropic-ai/claude-agent-sdk`; `query({ prompt, options })` is an async generator of messages; `options.systemPrompt`, `options.allowedTools`, `options.disallowedTools`, `options.permissionMode: 'dontAsk'`, `options.mcpServers`, `options.model`, `options.maxTurns`; stop with the query object's `interrupt()` and `close()`; in-process tools through `tool(name, description, zodShape, handler, { annotations: { readOnlyHint: true } })` and `createSdkMcpServer({ name, tools })`, allowed as `mcp__<server>__<tool>`; the npm package bundles the Claude Code binary as an optional dependency and `options.pathToClaudeCodeExecutable` overrides where to find it (needed when packaged in asar: unpack the SDK with electron-builder `asarUnpack`). Model IDs for the settings list come from Anthropic's current model page at M6, not from memory; the live list on 2026-10-10 reported `claude-fable-5-1`, `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`. The Haiku ID is `claude-haiku-5-5` everywhere (`KNOWN_MODELS` in `src/shared/claude.ts`).

- The question panel (A21) is a fifth Claude feature: a conversation with read-only in-process MCP tools (search entries, get entry, timeline for a year, relatives, get chapter) and `propose_change`; its system prompt forbids prose and instructs a one-sentence refusal. The other four features: session briefs, continuity prose checks, chapter summaries, import proposals. Each is a function in `src/main/claude/features/` that takes a deterministic input (the manifest contents, the chapter text plus its selected entries, the chapter text, or the imported document) and returns structured output validated with zod.
- Each feature calls the Agent SDK `query()` with `permissionMode: 'dontAsk'`, no built-in tools (`allowedTools` limited to the app's own `mcp__bible__*` tools, `disallowedTools` covering Bash, Edit, Write, WebFetch, WebSearch). The four structured features get all their material in the prompt and only the `propose_change` tool (import proposals and alignment findings) or no tool at all (briefs, summaries). The panel gets the read-only tools plus `propose_change`. `propose_change` writes only to the `proposals` collection (AI-3).
- Every system prompt contains the sentence "Never draft prose for the novel. Produce only the structured output requested." A unit test asserts it is present in every feature prompt, and a static test asserts no renderer channel sends free-form user text to any Claude feature (AI-4).
- Streaming partial messages feed the feature's output pane; an AbortController backs the Stop button.
- The model is read from settings per feature (DB-4): briefs and alignment checks (CC-3) default `claude-opus-5-5`; chapter summaries, import proposals, and the question panel default `claude-sonnet-5-5` (`DEFAULT_MODELS` in `src/shared/claude.ts`).
- In the test suite the SDK is replaced by a recorded-response fake behind the same interface (`src/main/claude/client.ts` exports an interface; `fake.ts` and `sdk.ts` implement it).
- If the key is unset or rejected, the app says so and opens the settings screen.

## Google Drive

Checked 2026-10-11 against Google's "OAuth 2.0 for iOS & Desktop Apps", "Choose Google Drive API scopes", "Configure the OAuth consent screen", and the Drive export-formats reference.

- **Sign-in (GD-1).** `src/main/drive/oauth.ts`: a one-shot HTTP listener on `127.0.0.1:<random port>` is the redirect URI (Google's recommended desktop method; custom schemes and copy-paste codes are no longer supported). The consent page opens with `shell.openExternal` in the system browser, never in an app window. PKCE with S256, a random `state`, `access_type=offline`, `prompt=consent` (so a refresh token always comes back), no `include_granted_scopes` (Google's incremental authorization is not available to installed apps, so Allow export asks for `drive.readonly` and `drive.file` together). The token exchange sends the client secret, which Google says installed apps cannot keep confidential but still accepts.
- **Scopes.** Import uses `drive.readonly`; export adds `drive.file` only when Tommy clicks Allow export. Why not narrower for import: `drive.file` is Google's non-sensitive recommendation, but it grants access only to files opened through the Google Picker (a web widget that cannot run in the locked-down renderer without loosening ARCH-1) or created by the app, it is read-write rather than the read-only access GD-1 asks for, and it cannot see files added later to a linked folder (GD-2, GD-3). `drive.metadata.readonly` cannot download content. So `drive.readonly` is the narrowest scope that does the import job; it is a restricted scope, which only means the unverified-app screen for Tommy's own Testing-mode client. Export uses `drive.file` alone for writing (GD-4: "access limited to files the app creates"); the app writes only into folders it created (tagged with a private `appProperties` key), and Tommy chooses among those or makes a new one.
- **Secrets (ARCH-5).** Keychain service `novel-companion-google`: account `oauth-client` holds `{ clientId, clientSecret }`, account `oauth-tokens` holds the refresh token, the current access token, its expiry, granted scopes, and the account email. Nothing else stores them; the renderer gets only `drive.status` (configured, connected, email, a masked client ID). Disconnect revokes at Google (best effort, 5 s) and deletes `oauth-tokens` (GD-5). An `invalid_grant` on refresh (the 7-day Testing expiry) deletes the tokens and says to connect again.
- **Network (ARCH-1).** All Google calls are made by main with Node's global `fetch`, which does not pass through the renderer session's `webRequest` filter. The renderer allowlist in `src/main/index.ts` is unchanged; no Google host was added to it or to the CSP.
- **Linking and changes (GD-2, GD-3).** Links and the Drive version last brought in per file live in the bible's `meta` document `drive` (`{ links, seen }`), written through `Repository.setDriveState`. A check calls `files.get` for each linked file and walks linked folders (four levels, 1,000 files); `classifyFiles` in `src/shared/domain/drive/files.ts` reports new, changed (Drive `modifiedTime` later than the version seen), unchanged, or missing. The renderer runs a check when a bible opens (launch notice) and on the Check button. Nothing is imported by a check.
- **Import through M5 (GD-2, IM-7).** `drive.open` fetches the file (Google Docs exported as .docx, Sheets as .xlsx, Office files downloaded) and hands it to the import pipeline through `ImportDeps.bridge`, so mapping, preview, saved mappings, the compare step, ED-7 approval, and IM-7 newer-source-wins all run unchanged. The recorded file name is the Drive name plus `.docx` or `.xlsx`, and the source's modified time is Drive's `modifiedTime`. Applying a comparison of a Drive file records its version as seen (`ImportDeps.onApplied`); Mark as reviewed does the same without importing.
- **MS-1 seam for M7.** `fetchDriveFile(fileId)` in `src/main/drive/index.ts` returns `{ data, fileName, modifiedAt, kind, mimeType }`; pass `data` and `{ fileName, modifiedAt }` to `parseDocxBuffer` or `parseWorkbookBuffer`. Read-only (MS-5).
- **Chapters from Google Docs (MS-1, wired at integration).** `gdocSource(fetchDriveFile)` in `src/main/session/sources.ts` is the `ManuscriptSource` with id `gdoc`, registered at startup with `registerManuscriptSource`. It reads the Doc as .docx through `fetchDriveFile` and runs the same `parseDocxBuffer` and `blocksToBody` as a Word file, so italics, headings, and scene breaks survive alike; the chapter is linked as `manuscriptSource: gdoc:<Drive file ID>`, so "Read the linked file again" fetches the current Doc and shows the MS-4 diff. A source says where it is picked (`picker: 'dialog' | 'drive'`): a Google Doc is chosen in the page with M9's Drive browser in pick mode (`DriveDocumentPicker` in `src/renderer/src/workspace/drive.tsx`, one document, nothing linked), and `manuscript.read` carries the chosen file ID as `locator`. Without a Drive connection the picker says to connect in Settings. Nothing in the path writes to Drive (MS-5).
- **Export (GD-4).** `drive.export` writes a new folder `<bible name> <UTC time>` inside the chosen export folder: `<bible id>.json` (exactly `exportBibleJson`, BK-3) and one folder per section with one Markdown file per live entry (`bibleMarkdown` in `src/shared/domain/drive/markdown.ts`; custom entries under their section's name).
- **Tests.** `tests/helpers/fakeGoogle.ts` is a fake Google (OAuth consent, token, revoke, Drive v3 files, export, multipart upload) on 127.0.0.1. Integration tests drive `DriveService` and the IPC handlers against it with an in-memory secret store; e2e sets `NOVEL_COMPANION_TEST_GOOGLE_BASE` (honoured only for a 127.0.0.1 address, and in a packaged build only under the test exception, see "Local development"), which also swaps the keychain for memory. Tommy's manual check of the real flow is in `docs/DRIVE-SETUP.md`.

### Claude runtime (built in M6)

Every Claude call goes through `ClaudeRuntime` in `src/main/claude/runtime.ts`. It reads the key (`keys.ts`, keychain service `novel-companion-anthropic`) and the model for the feature (`settings.ts`, a JSON file `claude-settings.json` in the app's data folder holding models and the per-bible AI-6 confirmation, never a secret), refuses to send anything before the disclosure is confirmed for the open bible, saves the input before sending, streams, stops, validates, queues proposals, and saves the outcome. A failure writes nothing to the bible and keeps the input (AI-7).

```ts
// src/main/claude/runtime.ts
interface FeatureDefinition<I, O> {
  feature: 'briefs' | 'alignment' | 'summaries' | 'importProposals';
  instructions: string;                 // feature text; systemPrompt() prepends the shared rules and the AI-4 sentence
  input: z.ZodType<I>;                  // the deterministic input, validated first
  output: z.ZodType<O>;                 // structured output; sent as outputFormat json_schema, validated with zod
  title(input: I, session: OpenBible): string;
  build(input: I, session: OpenBible): { prompt: string; given: EntryRefWire[] }; // deterministic
  proposals?(output: O, input: I, session: OpenBible): (ProposalDraft | { summary: string; problem: string })[];
  maxTurns?: number;
}
runtime.runFeature(session, def, rawInput, runId): Promise<{ runId; conversationId; done: Promise<ClaudeRun> }>
runtime.ask(session, { runId, conversationId, question })   // the question panel
runtime.stop(runId)
```

- **Adding a feature (M7 briefs and summaries, M8 alignment).** Write `src/main/claude/features/<name>.ts` exporting a `FeatureDefinition`, add it to `FEATURES` in `features/index.ts` (the AI-4 test walks that list), and add one IPC channel to `claudeContract` in `src/shared/claude.ts` whose request carries IDs only (a renderer-picked `runId` plus the IDs of the material) and whose handler in `src/main/claude/handlers.ts` calls `runtime.runFeature`. Put any manuscript or imported text in the prompt through `material(label, text)` (AI-5). Return proposals as `ProposalDraft`s; the runtime checks each against the schema and the read model and queues it with `Repository.propose` (source `claude`), and reports any it refused.
- **Runs are saved** in the bible's `conversations` collection (schema version 7, index `{ modifiedAt: -1 }`) by `store.ts`, the one place that writes it. A panel conversation is one document with many turns; a feature run is one document with one turn, its `input`, and its validated `output`. Each turn records the model, status (`running`, `done`, `stopped`, `failed`), the error kind and message, the entries read or given (AI-2), and the proposal IDs. Saves write one turn at a time (`$push` a new turn, `$set` the matching turn), never the whole document. A conversation takes one running turn at a time; a second question while one streams is refused. `runtime.stopAll()` runs when the open bible changes and before the store closes on quit, and waits until each run is saved as stopped. A save that fails mid-run still ends the run with one `finished` event (`saveFailed`); `done` never rejects.
- **Streaming** goes to the renderer as `claude.stream` events (`text`, `read`, `proposal`, `finished`) keyed by the `runId` the renderer chose, so it listens before the run starts. `useRunStream(runId)` in `src/renderer/src/workspace/claude.tsx` follows one run; `ClaudeErrorNote`, `EntriesRead`, and `ProposalsNote` render its state.
- **Tools** (`tools.ts`): `search_entries`, `get_entry`, `timeline_for_year`, `relatives_of`, `get_chapter` read the read model through the shared domain functions; `propose_change` writes a proposal only. A static unit test holds `tools.ts` to that.
- **Client** (`client.ts`): `ClaudeClient.run(request, signal)` yields `text`, `toolCall`, and one `result`, or throws a typed `ClaudeFailure`. `sdk.ts` implements it with `query()` (`tools: []`, `allowedTools` of `mcp__bible__*`, `disallowedTools` of every built-in, `permissionMode: 'dontAsk'`, `settingSources: []`, `persistSession: false`, `includePartialMessages: true`, `outputFormat` for features, an `env` built from nothing with the key and telemetry off, `CLAUDE_CONFIG_DIR` in the app's data folder). `fake.ts` replays `fixtures/claude/recordings.json` (matched by feature and prompt text, running the real tools) and fails plainly on a request it has no recording for. `NOVEL_COMPANION_TEST_FAKE_CLAUDE=1` (`src/main/ipc/handlers.ts`, unpackaged, or packaged under the test exception) is an older, separate switch that registers a stand-in for the session brief and summary seams (M7); one e2e test uses it, and it folds into `NOVEL_COMPANION_TEST_CLAUDE` once the Claude runtime is wired to the briefs and summaries. End-to-end runs set `NOVEL_COMPANION_TEST_CLAUDE=1` (honoured outside a packaged app, and in one only under the test exception in "Local development") for the fake, a key held in memory, and a fake models list.

### Briefs and summaries through the runtime (wired at integration)

M7 asks for Claude through two small services in `src/main/session/claude.ts` (`BriefSynthesizer`, `ChapterSummarizer`). `runtimeSessionClaude(runtime, current, keys)` in `src/main/claude/session.ts` implements both as ordinary feature runs and is registered at startup in `src/main/ipc/handlers.ts` (unless `NOVEL_COMPANION_TEST_FAKE_CLAUDE=1` in an unpackaged build, which keeps M7's `fakeSessionClaude()` stand-in). Both are null while no API key is stored, so the app falls back to the structured brief (SB-7) and a hand-written summary.

- **Briefs** (`features/briefs.ts`, SB-4, SB-5, DB-2). Input: the selection's label, year, strand labels, manifest, and `briefMaterial(selection)`, saved with the run. The prompt is that material only, wrapped with `material()` (AI-5), each entry as `[ID] title (group; status; strand): note. detail.`; no tools. Output: structured items `{ text, status, strand, cites }` in `characters`, `worldEvents`, `culture`, free `sections`, and `plannedAhead`. Code, not Claude, lays the Markdown out (`renderBrief`): the three DB-2 lead sections first under the `LEAD_SECTIONS` headings and always present ("Nothing selected." when empty), canon apart from planned material per strand, every item cited as `[[ID]]`, an item marked canon only when every entry it cites is canon, an item citing only a planned-ahead entry moved under "Planned ahead (after <year>)", then the SB-6 "Over budget" and "Left out" notes from the selection. `citationProblems` and `uncitedLines` then check it as for any brief; app notes (the opening line, "Left out", "Over budget") are not claims and are not flagged.
- **Summaries** (`features/summaries.ts`, MS-2). Input `{ chapterId }`; the chapter's imported text from the read model goes in as material; output `{ summary }`. The draft is returned for approval; nothing is written to the chapter.
- **Models** (DB-4). One settings key per feature, shared by M6 and M7: `briefs` (default `claude-opus-5-5`) and `summaries` (default `claude-sonnet-5-5`), resolved by `ClaudeRuntime.modelFor`. Settings shows both selects, and the brief window and size budget (stored in the bible) as the "Session briefs" panel.
- **Streaming and Stop** (AI-1). `session.start`, `brief.regenerate`, and `chapter.summarize` take an optional renderer-picked `runId`; the page follows `claude.stream` for it and Stop calls `claude.stop`. `useClaudeRun` (`src/renderer/src/workspace/sessions/claudeRun.tsx`) shows the AI-6 disclosure on the first use in a bible, the streamed character count, and Stop. A stopped or failed run is saved as such in `conversations`, and the brief falls back to the structured one with the reason in its note.
- **Recordings** (T-3). `fixtures/claude/recordings.json` holds a Chapter 6 brief (all citations in the manifest), a Chapter 2 brief with an uncited line, a foreign citation, a planned entry called canon, and a later event in the wrong section, a Chapter 5 brief that waits to be stopped, and a Chapter 6 summary.

## Local development

- `npm run dev` runs against Atlas with the keychain connection string.
- To run against a throwaway local database instead, start a one-node replica set (the repository uses transactions; a plain `mongod` will not do), for example `MongoMemoryReplSet` from `mongodb-memory-server` with a fixed port and `dbPath`, and run `NOVEL_COMPANION_TEST_MONGODB_URI='mongodb://127.0.0.1:<port>/?replicaSet=testset' NOVEL_COMPANION_USER_DATA=<dir> npm run dev`. The variable is honoured only for a localhost address in an unpackaged build, and the keychain is not read. A packaged build ignores it unless `NOVEL_COMPANION_ALLOW_TEST_URI=1` is also set; that flag exists only for the packaged smoke test and the journey (M10, T-4) and is never set in normal use. When the test database is honoured (`testDatabaseHonoured()` in `src/main/secrets.ts`), the data folder comes from `NOVEL_COMPANION_USER_DATA` and the Drive tokens and the Claude key are held in memory, so a test run never touches the keychain or the real data folder. With the flag and a local test address (`testSeamsHonoured()`), a packaged build also honours the recorded Claude (`NOVEL_COMPANION_TEST_CLAUDE`, with `NOVEL_COMPANION_TEST_CLAUDE_RECORDINGS` naming the file, since the package holds no fixtures), the fake Google (`NOVEL_COMPANION_TEST_GOOGLE_BASE`), and the file pickers (`NOVEL_COMPANION_TEST_PICK_*`, `_SAVE_PATH`, `_BIBLE_FILE`, `_BRIEF_EXPORT_DIR`); without them it refuses all of these. The proposal seam (`test.propose`) and the stop prompt switches are refused by every packaged build. `npm run test:journey` drives the packaged app in `release/`; `scripts/ensure-package.ts` runs `npm run package` first when it is missing or older than the source.

## Builder workflow

M8 and M10 are being built now, as Opus sub agents, under this protocol (A32; A30 is withdrawn). M10 is split into settings and offline, performance and accessibility and errors, and packaging and journey. The final audit runs after M8 merges.

A builder gets the milestone's criteria, this file, and the files it may touch. It writes code and tests, runs `npm test` until green, and reports which tests cover which criteria. The architect runs `npm test` again and then sends the spec and the code (not the builder's report) to a fresh reviewer.
